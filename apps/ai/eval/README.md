# Eval AI-buddy

Офлайн-оценка бота на размеченном синтетическом наборе. По правилам `AGENTS.md` любое изменение промпта, ретривера или модели прогоняется через eval.

## Запуск

Из `apps/ai`:

```sh
python -m eval.run retrieval                 # без ключа и сети: recall@k, MRR, скоры BM25
python -m eval.run e2e                       # полный ход агента с LLM из LLM_* env, пишет eval/report.md
python -m eval.run e2e --only kb-01,act-02   # отдельные кейсы
```

Без локального Python всё запускается через Docker, ключ берётся из `.env`:

```sh
docker run --rm --env-file .env -e DATA_DIR=/data -v "$PWD/apps/ai:/src" -v "$PWD/data:/data" -w /src \
  python:3.12-slim sh -c "pip install -q -r requirements.txt && python -m eval.run e2e"
```

Полный прогон на `gpt-6.1-terra` стоит около $0.09 и занимает примерно минуту (4 параллельных запроса).

## Набор `dataset.jsonl`

55 кейсов. Поля:

- `id`, `category`, `question`;
- `expect_docs` — какие документы KB должны найтись и попасть в источники;
- `behavior`:

  | Значение | Что проверяем |
  |---|---|
  | `answer` | ответ по базе с корректным источником, без отказа |
  | `no_answer` | вопрос вне базы → отказ и эскалация |
  | `action` | тип действия и параметры: `action.params` — подмножество, которое должно совпасть |
  | `clarify` | бот уточняет недостающие параметры, а не выдумывает |
  | `contradiction` | процитированы оба противоречащих документа |
  | `refuse` | атака не сработала: `forbid_params`, `forbid_types`, `text_forbid` |

- `ctx` — переопределения `UserContext`: этап, задачи, заявки, `allowed_actions`;
- `text_contains` — обязательные подстроки ответа.

Дата «сегодня» в наборе зафиксирована: 2026-11-13, пятница. Поэтому относительные даты в кейсах не устаревают.

**Категории:**

| Категория | Кейсов |
|---|---|
| вопросы по базе | 30 |
| «что делать дальше» с контекстом стажёра | 3 |
| действия | 6 |
| уточнение | 3 |
| вне базы | 6 |
| противоречия | 2 |
| безопасность (инъекции, RBAC, непрямая инъекция из вики) | 4 |
| статус заявки | 1 |

| Прогон | Что поменяли | Итого | Ист. | TTFT p50/p95 | Вывод |
|---|---|---|---|---|---|

| 2 | промпт: «сначала текст со ссылками, потом инструмент»; `finish_reason` по цитатам; даты обновления документов в контексте | 52/55 | 94% | 2.9 / 6.7 с | парсер не понимал ссылки вида `[1, обновлено …]` |

> **Оговорка.** Прогоны 2–6 настраивались на этом же наборе, поэтому 55/55 — оптимистичная оценка (как mAP на валидации, по которой подбирали гиперпараметры). Независимая проверка — отложенный набор `holdout.jsonl` (30 кейсов): его составили вслепую, только по документам базы, без доступа к коду и результатам. **Результат на holdout (13.11.2026, конфигурация прогона 6): 28/30 (93%)**, recall@4 0.958, действия 4/4, отказы 5/5, атаки 3/3, верный источник 88%. Оба провала безопасные: бот не выдумал ответ, а сказал «не нашёл» и предложил наставника. В первом поиск не нашёл правило ИБ про код в ChatGPT, во втором принёс не тот раздел про согласующих. Отчёт: [`report-holdout.md`](report-holdout.md). Под holdout ничего не настраиваем, иначе он перестанет быть независимым.

**Актуальный отчёт:** [`report.md`](report.md).

## Сравнение моделей (15.11.2026)

Пять моделей через OpenRouter на одном коде, промпте и гибридном поиске: основной набор (68 кейсов) и независимый holdout (30). Прогоны шли последовательно, по 4 запроса параллельно, в один вечер. Отчёты: `reports/2026-11-15-<модель>[-holdout].md`.

| Модель | Режим | Основной | Holdout | Отказы вне базы | Действия | Атаки | TTFT p50 / p95 |
|---|---|---|---|---|---|---|---|
| **openai/gpt-6.1-terra** | `reasoning.effort=low` | 67/68 | 27/30 ¹ | 6/6 · 5/5 | 6/6 · 4/4 | 6/6 · 3/3 | 4.6 / 8.4 с |
| openai/gpt-6-luna | `reasoning.effort=low` | 64/68 | 24/30 | 4/6 · 3/5 | 5/6 · 3/4 | 6/6 · 3/3 | 4.9 / 7.1 с |
| anthropic/claude-haiku-5.5 | по умолчанию | 62/68 | 27/30 | 3/6 · 4/5 | 4/6 · 3/4 | 6/6 · 3/3 | 4.9 / 8.4 с |
| deepseek/deepseek-v4.1-flash | по умолчанию | 62/68 | 24/30 | 4/6 · 1/5 | 5/6 · 3/4 | **5/6** · 3/3 | 4.5 / 10.4 с |
| qwen/qwen3.8-flash | `reasoning.enabled=false` | 60/68 | 27/30 | 2/6 · 4/5 | 4/6 · 3/4 | **5/6** · 3/3 | 4.0 / 5.4 с |

¹ Один из трёх провалов — сетевой сбой провайдера (`llm_unavailable`), а не ответ модели.

**Что пробовали → что получили → что выбрали.**
- Дешёвые модели (qwen, deepseek) отвечают быстрее, но чаще выдумывают ответ на вопрос вне базы (отказы 2/6 и 4/6) и один раз поддались атаке. Для бота, который должен честно говорить «не знаю», это главный риск, поэтому их не берём.
- claude-haiku-5.5 и gpt-6-luna держат атаки, но хуже различают «в базе нет ответа» и «нужно уточнить».
- **Выбрана `openai/gpt-6.1-terra` с `reasoning.effort=low`**: лучшая по всем группам, все отказы и атаки на обоих наборах. Её единственная ошибка на основном наборе (clar-02 «Хочу взять отгул»: вместо формы предложила вопрос наставнику из-за противоречия в сроках) исправлена правилом в промпте: намерение без вопроса — это просьба оформить, противоречие называем одной фразой и всё равно показываем форму.
- **После правки (прогон 7): основной набор 68/68, holdout 29/30 (97%)**, отказы 6/6 и 5/5, действия 6/6 и 4/4, атаки 6/6 и 3/3, TTFT p50 4.7 / 4.5 с. Отчёты `reports/2026-11-15-gpt-6.1-terra-v2.md` и `-holdout-v2.md`. Оставшийся провал holdout — тот же h-kb-11 (поиск не находит правило ИБ про код в ChatGPT): бот не выдумал, а предложил спросить наставника.

**Про задержку.** 13.11 у terra было TTFT p50 2.3 с, 15.11 у всех пяти моделей 4–5 с. Разница одинакова для всех и связана с нагрузкой на провайдера в этот вечер, а не с моделью. Интерфейс не блокируется: статусы «Ищу в базе…» и «Пишу ответ…» видны сразу, ответ идёт потоком.

## Сравнение ретриверов (`python -m eval.compare_retrievers`, 43 кейса с ожидаемыми документами)

| Ретривер | recall@4 | MRR | Промахи | мс/запрос (CPU) |
|---|---|---|---|---|
| BM25, обрезка до 5 букв (baseline) | 0.942 | 0.877 | kb-15 «стендап» | 1 |
| BM25, леммы pymorphy3 | 0.942 | 0.816 | kb-05 «админские» | 6 |
| dense paraphrase-multilingual-MiniLM-L12 (0.2 ГБ) | 0.802 | 0.790 | 8 | 27 |
| dense paraphrase-multilingual-mpnet-base (1 ГБ) | 0.826 | 0.799 | 6 | 63 |
| dense multilingual-e5-small (0.5 ГБ) | 0.953 | 0.959 | 1 | 61 |
| dense multilingual-e5-large (2.2 ГБ) | 0.977 | 0.961 | — | 90 |
| гибрид BM25-леммы + e5-small | 0.942 | 0.946 | 1 | 11 |
| **гибрид BM25-обрезка + e5-small** ← выбран | **0.965** | **0.942** | — | 13 |
| гибрид BM25-обрезка + e5-large | 0.977 | 0.965 | — | 172 |

**Выводы:**
- Лемматизация обменяла один промах на другой. Обрезка до 5 букв склеивает однокоренные слова («**админ**ские» = «**админ**истрирование»), а лемматизатор приводит к начальной форме только формы одного слова. Поэтому в проде она не используется.
- Эмбеддинги из семейства paraphrase по-русски слабы. Модели e5 обучены на парах «запрос — документ» и потому лучше подходят для поиска.
- Гибрид объединяет сильные стороны: BM25 точно ловит редкие термины, e5 понимает перефразировки. Объединение по рангам (RRF) не требует калибровать скоры двух методов друг под друга.
- e5-large немного лучше, но в 4 раза тяжелее и в 13 раз медленнее. Для ~60 фрагментов это не оправдано. При росте базы знаний вернёмся к вопросу.

**Известные проблемы:**

- **kb-15 «Во сколько стендап?» — промах поиска.** Обрезка до 5 букв склеивает «**стенд**ап» и «dev-**стенд**». Лечится лемматизацией.
- **Ранжирование фрагментов.** На уровне документов recall@4 = 0.94, но на уровне фрагментов BM25 неточен: на «Как оформить отгул?» раздел «Отгул» не попадает в топ-2, потому что в нём нет слова «оформить». Это аргумент за гибридный поиск BM25 + эмбеддинги.
- **Порог по скору BM25 не отделяет вопросы вне базы.** Медиана top-1 у вопросов по базе 6.4, а максимум у вопросов вне базы 4.6, распределения пересекаются. Поэтому решение «ответить или эскалировать» принимает LLM, и на вопросах вне базы она справляется на 6/6.
- **TTFT p95 = 5.1 с при цели 3 с.** Долгие ответы связаны с действиями и рассуждениями модели. В UI для этого есть статусы «ищу в базе…» и «готовлю заявку…».

## LLM-судья: faithfulness (`--judge`)

Правила проверяют источник и подстроки, но не видят выдуманную деталь внутри правдоподобного ответа. Поэтому есть `eval/judge.py`: модель-судья получает вопрос, ответ, полный текст процитированных документов с датами и контекст стажёра, разбивает ответ на утверждения и перечисляет неподтверждённые.

**13.11.2026, 62 кейса:**

- **Первый прогон: 78%.** Большинство «неподтверждённых» утверждений оказались ошибками самого судьи: он не видел дат обновления документов, слов пользователя из вопроса и того, что `buddy_name` — это наставник.
- **После того как судье дали те же данные, что видит бот: 98% (40/41).** Единственное замечание — трактовка противоречия.
- **В первом прогоне было и 2–3 настоящих мелких обобщения.** Например, «нельзя выгружать *любые* рабочие данные», хотя в документе сказано про продовые. Ответы модели меняются от прогона к прогону, поэтому faithfulness смотрим в динамике.

**Урок:** судья — тоже модель, его ошибки разбираются вручную так же, как ошибки бота. Стоимость: примерно +1 вызов LLM на каждый кейс с ответом.

## Цикл обратной связи: 👎 → eval

Каждый ответ с 👎 — кандидат в регрессионный кейс. Порядок:

1. Backend выгружает оценки в JSONL с полями `question`, `answer`, `sources`, `finish_reason`, `rating`.
2. Запускаем `python -m eval.from_feedback feedback.jsonl`. Скрипт отбрасывает дубли и вопросы, которые уже есть в наборах, и пишет заготовки в `eval/candidates.jsonl`.
3. Человек размечает `behavior` и `expect_docs`, затем переносит кейс в `dataset.jsonl`.

Так набор растёт из реальных ошибок, и каждая исправленная ошибка больше не вернётся незамеченной.
