# AI-Buddy — спецификация Go Backend

Актуально на 15 ноября 2026 года. Источник истины для HTTP-маршрутов — `apps/backend/internal/handler/`; для схемы данных — `apps/backend/migrations/`; машинный контракт — [`contracts/backend.openapi.json`](../contracts/backend.openapi.json). Эта спецификация описывает реализованный backend, а не устройство AI или Web.

## Назначение и границы

Backend предоставляет авторизацию, чек-листы адаптации и прогресс, проверку результатов наставником, персональные задачи, заметки, календарь, заявки на корпоративные инструменты, обратную связь и подсказки. Данные пользователей и прогресс хранятся в PostgreSQL. Синтетический справочник Mock HR загружается из JSON при запуске; `sync-hr` отдельно синхронизирует его с локальными учётными записями. Backend обращается к AI по HTTP для чата и подсказок. Реальные HR, аналитические и корпоративные системы не подключены.

Web обращается к `/api/*` через proxy к backend; подтверждённый здесь интерфейс — только эти HTTP-контракты. `/health` проверяет доступность процесса, но не готовность PostgreSQL или AI.

## Компоненты и стек

| Компонент | Реализация и ответственность |
|---|---|
| HTTP API | Go 1.26.0, `net/http` ServeMux, handlers, middleware JWT/RBAC, JSON-ответы |
| Сервисы | Правила авторизации, прогресса, HR sync, корпоративного каталога, feedback и hint worker |
| Репозитории | `database/sql` и pgx-драйвер, PostgreSQL 16, транзакции и ограничение доступа по владельцу |
| Миграции | SQL в `apps/backend/migrations/`, применяются отдельно через `cmd/migrate` |
| Mock HR | `data/corporate_employees.json` для in-memory справочника и ручного `cmd/sync-hr` |
| AI | Внешний для backend HTTP-сервис, `POST /chat` и `POST /hint`; детали ML здесь не определяются |
| Mock analytics | Запись события feedback в PostgreSQL через локальный адаптер; `cmd/retry-feedback` повторяет неуспешную доставку |

`internal/app.Run` загружает Mock HR до открытия БД, создаёт зависимости, запускает фоновый hint worker и HTTP-сервер на `:8080`. Compose собирает backend из `apps/backend/Dockerfile`, запускает отдельные AI, Web и PostgreSQL 16 сервисы. Доступ backend через Web проксируется на `/api`; способ отображения данных Web не входит в эту спецификацию.

## Модель данных

| Таблица | Назначение и основные связи |
|---|---|
| `users` | Локальный пользователь; уникальные email без учёта регистра и непустой `corporate_id`; для стажёра `buddy_id` и `teamlead_id` ссылаются на `users` |
| `auth_sessions` | Сессия пользователя, хеш refresh token, срок действия и время отзыва |
| `checklists` | Один общий каталог и профессиональный каталог на профессию (`backend`, `frontend`, `ml`) |
| `checklist_stages` | Стадии чек-листа с номером недель, целью и ожидаемым результатом |
| `checklist_items` | Упорядоченные задачи стадии; `assigned_user_id` задаёт персональную задачу, `requires_review` — необходимость проверки, `due_at` — срок |
| `user_checklist_progress` | Состояние задачи конкретного стажёра, `completed_at`, `activated_at`; уникальна пара пользователь/задача |
| `checklist_item_submissions` | Попытки сдачи задачи, статус и решение buddy; частичный уникальный индекс разрешает только одну ожидающую попытку на запись прогресса |
| `notes`, `calendar_events` | Личные записи с `user_id` |
| `corporate_access_requests` | Заявка на инструмент, владелец, ключ идемпотентности и номер тикета |
| `checklist_feedback`, `mock_analytics_feedback` | Обратная связь стажёра и локальная имитация её доставки в аналитику |
| `task_hints` | Очередь, результат, попытки и отметка прочтения подсказки для записи прогресса |

Связи и ограничения определены миграцией [`00001_init.sql`](../apps/backend/migrations/00001_init.sql). Каталог чек-листов наполняет `cmd/init-catalog`; миграция создаёт структуру, а не весь каталог. Пароли хранятся только в виде хеша.

## Роли, сессии и доступ

Роли: `intern`, `buddy`, `teamlead`. `POST /api/auth/login` и `POST /api/auth/refresh` доступны без access token. Остальные `/api/*` требуют `Authorization: Bearer <JWT>`; `/health` открыт. Access JWT подписывается HS256, проверяются подпись, срок, issuer и пользователь. Обычный login выдаёт access и refresh token. Refresh token хранится в БД только в виде хеша, при обновлении ротируется внутри транзакции; повторное использование отозванного/старого токена отклоняется. Logout требует действующий access JWT и refresh token в теле, отзывает сессию. Access JWT с идентификатором сессии проверяется против `auth_sessions`; middleware сохраняет совместимость со старыми JWT без идентификатора сессии и не выполняет для них проверку таблицы сессий.

| Действие | Доступ |
|---|---|
| Свои чек-листы, общий прогресс, завершение и сдача задач, история сдачи, feedback | Только `intern` |
| Ожидающие проверки и решение по ним | Только `buddy`, только назначенные стажёры |
| Создание персональной задачи | Только `teamlead`, только назначенный стажёр |
| Список назначенных стажёров и их прогресс | `buddy` или `teamlead`; buddy видит оба чек-листа, teamlead — профессиональный |
| Профиль, заметки, календарь, подсказки, чат, собственные корпоративные заявки | Любая аутентифицированная роль; данные ограничены владельцем |
| Каталог корпоративных инструментов и создание заявки | Только `intern`; инструкция по одному инструменту проверяет право в Mock HR |

Неназначенный стажёр и чужой объект обычно дают `404`, чтобы не раскрывать их наличие. `403` означает недостаточную роль или корпоративное разрешение. Локальное назначение в `users` является авторитетным для доступа к данным приложения; корпоративный профиль сверяется со снимком Mock HR.

## Чек-листы и прогресс

Стажёр видит общий и соответствующий текущей профессии профессиональный чек-лист. Профессиональные записи старого трека остаются в БД после смены профессии, но не выдаются как текущий трек и не допускают новых переходов прогресса. Стадии содержат задачи с позицией и временным диапазоном недель. Обычные задачи идут последовательно **внутри каждого чек-листа**; общий и профессиональный чек-листы независимы. Завершение или сдача активной обычной задачи разблокирует следующую обычную задачу в том же чек-листе. Персональные задачи при этом пропускаются.

Состояния `user_checklist_progress`: `unavailable` → `active` → `completed`; после одобрения buddy — `verified`. Для задачи без проверки `POST .../complete` переводит `active` в `completed`; повторное завершение уже завершённой задачи идемпотентно. Задача с `requires_review` сдаётся через `POST .../submissions` с непустым `result_text` или `result_url`: создаётся попытка `pending`, прогресс получает `completed`. Buddy может одобрить: попытка `approved`, прогресс `verified`; либо отклонить с непустым комментарием: попытка `rejected`, прогресс снова `active`, время завершения сбрасывается. Повторное решение по одной попытке запрещено. Открытая задача сначала только **доступна**: `active` с `activated_at = NULL` (в API `started: false`), на доске она стоит первой в колонке «Задачи». Стажёр сам берёт её в работу через `POST /api/checklist-items/{itemID}/start` (`activated_at = now()`, `started: true`, колонка «Активно»); повторный вызов идемпотентен, для `unavailable`/завершённой задачи — `409`. Так открываются первая задача чек-листа, следующая после завершения или сдачи и следующая после удаления текущей тимлидом. Воркер подсказок и отчёт о просрочке считают оценку времени от `activated_at`, поэтому не начатые задачи не считаются просроченными. Возвращённая на доработку задача и персональная задача тимлида сразу начаты.

**Подтверждённый процент** считается по каждому чек-листу: `completed_items / total_items × 100`. Для задачи без проверки учитывается `completed` (или `verified`); для задачи с проверкой — только `verified`. Ожидающая buddy задача не повышает подтверждённый процент. Общий прогресс объединяет числа общего и профессионального чек-листов. Разблокировка следующей обычной задачи происходит при сдаче стажёром, до решения buddy. Если buddy отклонил сдачу, ранее открытая следующая задача остаётся открытой. Это текущая бизнес-механика.

Прогресс изменяется в транзакции с блокировкой владельца и нужных записей. Ошибка на промежуточном шаге откатывает изменение статуса и открытие следующей задачи. Проверка текущей профессии выполняется при изменении. Чтение чек-листов использует согласованный снимок транзакции.

## Персональные задачи, заметки и календарь

Teamlead добавляет персональную задачу в профессиональный чек-лист назначенного стажёра на позицию с отсчётом от 1. Нужны заголовок, ожидаемый результат и положительная оценка времени; `requires_review` необязателен и по умолчанию `false`; `due_at` необязателен, в RFC 3339. Новая задача сразу `active`, статусы других задач не меняются; одновременно может быть несколько активных персональных задач. Вставка сдвигает позиции элементов, не ломая порядок обычных задач. Персональная задача не открывает следующую обычную задачу при завершении.

Заметки (`/api/notes`) и события календаря (`/api/calendar/events`) поддерживают создание, список, чтение, обновление и удаление. SQL-запросы ограничены `user_id`, поэтому чужие записи не попадают в списки и недоступны по ID. Для заметки нужен непустой заголовок; для события — непустой заголовок и `ends_at` позже `starts_at`.

## Mock HR и корпоративные заявки

`cmd/sync-hr` читает синтетический снимок, проверяет уникальность идентификаторов и email, роли, профессии и ссылки стажёров на buddy/teamlead. Синхронизация сериализуется advisory lock в транзакции; поиск идёт по `corporate_id`, а старые записи могут быть сопоставлены по email и роли. Для новых пользователей создаются локальные записи и начальные учётные данные в отдельном защищённом файле. Повторный запуск не создаёт дублей при неизменных идентификаторах; существующие локальные ID, хеши паролей и прогресс сохраняются. Отсутствующий в очередном снимке пользователь не удаляется. При смене профессии новый трек инициализируется, старый прогресс хранится как история. Неудача публикации файла учётных данных откатывает транзакцию; при неопределённом результате COMMIT файл сохраняют для разбора. Путь и содержимое учётных данных не должны попадать в репозиторий.

Справочник Mock HR backend читает **один раз при запуске** из `DATA_DIR/corporate_employees.json`; `sync-hr` не обновляет его в памяти работающего процесса. После изменения файла и ручной синхронизации нужен контролируемый перезапуск backend; в Compose JSON копируется в образ, поэтому сначала требуется пересборка backend-образа. Динамическая синхронизация не реализована.

Корпоративный каталог инструментов и инструкции строятся из Mock HR. Доступ к инструкции проверяется сервером, недостаточное право даёт `403`; отсутствие/недоступность mock даёт `404`/`503`. Стажёр создаёт заявку только с явным `confirm: true` и ключом идемпотентности. Один и тот же ключ того же пользователя и инструмента возвращает существующий тикет (`200`), новый — `201`; повторное использование ключа для другого инструмента даёт `409`. Список и чтение заявок ограничены владельцем. Это локальные mock-тикеты, а не реальные корпоративные обращения.

## Feedback и AI-контракты

`GET /api/checklists/{checklistID}/feedback` возвращает `{"feedback": null}` или сохранённый объект для собственного чек-листа. `POST` принимает `rating` 1–5 и комментарий длиной не более 4000 байт в UTF-8 по текущей проверке сервиса, сохраняет один отзыв после подтверждённого завершения **всех** задач чек-листа. Незавершённый чек-лист и повторная отправка дают `409`. Сохранение отзыва и доставка в mock analytics разделены: статус доставки хранится в БД, `cmd/retry-feedback` повторяет неуспешные доставки.

`POST /api/chat` принимает один JSON-объект `{"message":"..."}` без неизвестных полей. Сообщение не может быть пустым после trim и ограничено 2000 Unicode code points. Backend передаёт его в `POST <AI_URL>/chat` и ожидает JSON `answer`, `sources`, `mode: "mock"`; таймаут 10 с, недоступность или некорректный ответ AI превращаются в `502`. HTTP-контракт AI описан в [`contracts/ai.openapi.json`](../contracts/ai.openapi.json), внутренняя модель AI вне этой SDD.

Фоновый hint worker обрабатывает активные просроченные по оценке времени задачи: отправляет в `POST <AI_URL>/hint` заголовок, описание, ожидаемый результат и `estimated_minutes`, сохраняет текст подсказки в `task_hints`. Ошибки AI не ломают прогресс: есть повторные попытки и локальный fallback. `GET /api/hints`, `GET /api/checklist-items/{itemID}/hint` и `POST /api/hints/{hintID}/read` возвращают или обновляют только собственные подсказки. Генерация происходит асинхронно, поэтому сразу после активации задачи подсказки может ещё не быть.

## HTTP API и ошибки

Полные методы, параметры и основные ответы — в [`backend.openapi.json`](../contracts/backend.openapi.json). Группы реализованных маршрутов:

| Группа | Маршруты |
|---|---|
| Проверка и сессия | `GET /health`; `POST /api/auth/login`, `/api/auth/refresh`, `/api/auth/logout`; `GET /api/auth/me` |
| Стажёр | `GET /api/checklists`, `/api/progress`; `POST /api/checklist-items/{itemID}/complete`; `GET/POST /api/checklist-items/{itemID}/submissions`; `GET/POST /api/checklists/{checklistID}/feedback` |
| Buddy/teamlead | `GET /api/staff/interns`, `/api/staff/interns/{internID}/progress`; `GET /api/staff/teamleads`, `/api/staff/buddies`; `GET /api/buddy/submissions`; `POST /api/buddy/submissions/{submissionID}/review`, `/api/teamlead/interns/{internID}/checklist-items` |
| Личные данные | `GET/POST /api/notes`, `/api/calendar/events`; `GET/PUT/DELETE /api/notes/{id}`, `/api/calendar/events/{id}` |
| Корпоративный mock | `GET /api/corporate/me`, `/api/corporate/employees/{id}`, `/api/corporate/tools`, `/api/corporate/tools/{tool}`, `/api/corporate/access-requests`, `/api/corporate/access-requests/{id}`; `POST /api/corporate/access-requests` |
| AI через backend | `POST /api/chat`; `GET /api/hints`, `/api/checklist-items/{itemID}/hint`; `POST /api/hints/{hintID}/read` |

API отдаёт JSON-ошибки вида `{"error":"..."}`. Типичные коды: `400` — неверный JSON/параметры или переход, `401` — нет или недействителен токен, `403` — роль/разрешение, `404` — объект отсутствует или чужой, `409` — конфликт состояния/идемпотентности, `500` — внутренняя ошибка, `502` — ошибка AI, `503` — отключён Mock HR. Успешные ответы используют `200`, `201` или `204` по операции. Не всякий код применим к каждому маршруту; смотрите handler и OpenAPI.

## Технические решения и ограничения

- Синтетические данные служат демо; внешний HR и заявки не интегрированы. Флаг `CORPORATE_MOCK_UNAVAILABLE=1` имитирует недоступность справочника, `ANALYTICS_MOCK_UNAVAILABLE=1` — недоступность mock analytics.
- Локальные отношения buddy/teamlead и владение объектом проверяются на сервере. UI не является границей безопасности.
- Очередность обычных задач, персональные задачи и подтверждённый процент имеют разные правила; статус `completed` для review-задачи означает сдачу стажёром, а не одобрение buddy.
- `/health` не проверяет зависимости; ошибки AI изолируются на `/api/chat` и hint worker.
- Прежние JWT без идентификатора сессии поддерживаются middleware для совместимости; для них нельзя обеспечить немедленный отзыв через таблицу сессий.
- Проверка реализации: тесты находятся в `apps/backend`; интеграционные тесты используют отдельную `TEST_DATABASE_URL`, opt-in E2E — `RUN_E2E=1`. Эта спецификация не утверждает конкретный процент покрытия.
