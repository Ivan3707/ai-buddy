# Backend: роли, корпоративный mock и AI-контракт

## Состояние и запуск

Код рассчитан на Goose `00001`–`00007`. Миграция `00007` добавляет роль `teamlead`, nullable `users.teamlead_id`, `birth_date`, `employed_since` и таблицу `corporate_access_requests` с уникальным ключом `(user_id, idempotency_key)`. Старые записи сохраняют `NULL` в новых полях. Миграции и seed применяются только к заранее проверенной БД; основная `app` в ходе этой работы не обновлялась.

`data/corporate_employees.json` — синтетический справочник, загружаемый при запуске Backend. Он не содержит онбординг или прогресс. Локальная учётная запись сопоставляется по email, роли и профессии. Демо-идентичности: `buddy@demo.example`, `teamlead@demo.example`, `ml.intern@demo.example`, `ml.other@demo.example`. Для демонстрации эти локальные аккаунты создаются только в разрешённой БД. `cmd/bootstrap-buddy` по умолчанию создаёт buddy; `BOOTSTRAP_ROLE=teamlead` создаёт руководителя при тех же `BOOTSTRAP_BUDDY_EMAIL`/`BOOTSTRAP_BUDDY_PASSWORD`. Нужны также проверенные переменные PostgreSQL и миграция v7. Команда не меняет существующий аккаунт. `CORPORATE_MOCK_UNAVAILABLE=1` при запуске имитирует отказ корпоративного сервиса (HTTP 503).

Скрипт `apps/backend/scripts/seed_demo_ml_checklist_v1.sql` содержит три этапа и шесть заданий для профессии `ml`. Он рассчитан на Goose v7 и прекращает работу, если ML-чек-лист уже существует. Скрипт не запускается автоматически. Общий чек-лист также необходим для создания стажёра. Для проверки на `ai_buddy_test` без загрузки seed используется независимый тестовый ML-чек-лист.

## Права и маршруты

Все маршруты ниже, кроме `POST /api/auth/login` и `POST /api/auth/refresh`, требуют `Authorization: Bearer <access_token>`. Отзыв сессии работает через существующий refresh механизм.

| Маршрут | Доступ | Результат |
|---|---|---|
| `POST /api/users` | buddy | Создание intern с обязательными `teamlead_id`, `birth_date`, `employed_since`, именем, фамилией, департаментом, отделом и профессией. Buddy берётся из JWT. |
| `PUT /api/buddy/interns/{internID}/teamlead` | назначенный buddy | Назначение руководителя существующему стажёру, включая старые записи без `teamlead_id`. Тело: `{"teamlead_id":"<uuid>"}`; успешный ответ 204. |
| `GET /api/auth/me` | текущий пользователь | Профиль, `age_years`, `tenure_months`, назначенные buddy и teamlead. Для старых записей вычисляемые поля `null`. |
| `GET /api/progress` | intern | Сумма выполненных и всех заданий общего и профессионального чек-листов, включая персональные, процент, детали обоих чек-листов. |
| `GET /api/staff/interns/{internID}/progress` | назначенный buddy/teamlead | Buddy видит оба чек-листа и общий процент. Teamlead видит только профессиональный чек-лист и его процент. Чужой стажёр — 404. |
| `POST /api/teamlead/interns/{internID}/checklist-items` | назначенный teamlead | Добавление персонального задания в профессиональный чек-лист, позиция с 1. Завершённые задания сохраняют статус; уже активные остаются активными. |
| `GET /api/corporate/me` | сопоставленная корпоративная личность | Синтетический корпоративный профиль и разрешённые инструменты. |
| `GET /api/corporate/employees/{id}` | сам сотрудник или назначенный buddy/teamlead | Для доступа к чужому профилю проверяются и корпоративная связь, и локальное назначение. |
| `GET /api/corporate/tools/{tool}` | сотрудник с разрешённым инструментом | Публичная для этого сотрудника инструкция по заявке и `source=corporate-mock`; иначе 403. |
| `POST /api/corporate/access-requests` | intern с корпоративным разрешением | Создание заявки. Нужны `tool`, `idempotency_key` (8–128 символов) и `confirm: true`. Новый тикет — 201, повтор с тем же ключом и инструментом — 200; ключ с другим инструментом — 409. |
| `GET /api/corporate/access-requests` | владелец | Свои заявки. |
| `GET /api/corporate/access-requests/{id}` | владелец | Своя заявка; чужая — 404. |

Пример подтверждённого действия:

```http
POST /api/corporate/access-requests
Authorization: Bearer <access_token>
Content-Type: application/json

{"tool":"ml-platform","idempotency_key":"browser-action-12345","confirm":true}
```

Ответ `201`: `{"id":"<uuid>","tool":"ml-platform","ticket_number":"SD-<UUID>","status":"open","created_at":"<RFC3339>"}`. Номер и статус сохраняются в PostgreSQL; mock не переводит заявки в `approved`/`denied`. При недоступности mock возвращается 503 без новой заявки. Локальные заметки и календарь по-прежнему доступны только владельцу. Результаты заданий проверяет buddy, а персональные задания создаёт teamlead.

## Граница с AI

Текущий `POST /api/chat` принимает только `{"message":"..."}` и проксирует его в существующий AI `POST /chat`. Он предназначен для информационных ответов и не получает корпоративный справочник, чужой профиль или права на вызов Service Desk. `GET /api/checklist-items/{itemID}/hint` использует существующий AI `POST /hint`; подсказки хранятся в Backend. Backend никогда не исполняет действие на основании текста ответа LLM.

Для будущего запуска действия из чата AI-команде предлагается **новый, ещё не реализованный контракт**: AI возвращает отдельное структурированное предложение `{ "type": "access_request", "tool": "ml-platform", "requires_confirmation": true }` без вызова корпоративного API. Frontend показывает предложение, получает явное подтверждение пользователя и вызывает `POST /api/corporate/access-requests` с новым `idempotency_key`. Backend повторно проверяет JWT, корпоративную личность, список разрешённых инструментов и подтверждение. Ни предложение AI, ни текст чата не являются разрешением. Без согласования и реализации этого контракта естественно-языковое создание заявки через чат недоступно; клиент может использовать уже работающий прямой маршрут.

AI-чат не классифицирует произвольные запросы на чужие данные. Серверная защита действует на конкретных корпоративных маршрутах и SQL-запросах; защищённые корпоративные записи в AI-сервис не передаются. Ответ AI не является источником корпоративных прав и может содержать неточности. Для дополнительных защищённых источников нужен отдельный контракт структурированных запросов с проверкой Backend до чтения источника.
