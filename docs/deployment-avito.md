# Внедрение AI-buddy в компании

Практическая инструкция: как развернуть AI-buddy во внутреннем контуре компании (на примере Авито), что настроить, какие данные куда уходят и что проверить перед запуском. Поведение AI-функций описано в [SDD-002](specifications/002-ai-agent-chat.md), локальный запуск — в [README](../README.md).

> Всё, что сейчас лежит в `data/kb`, — синтетические демо-данные. Они не являются регламентами Авито. При внедрении их заменяет корпоративный Confluence.

## 1. Что разворачиваем

| Компонент | Состояние | Замечания |
|---|---|---|
| `web` (React) + Chrome-расширение | stateless | Статика за корпоративным ingress. Расширение раздаётся через managed-политику Chrome с `BACKEND_ORIGIN` прода. |
| `backend` (Go) | stateless, данные в PostgreSQL | Единственная точка входа: JWT, RBAC, `UserContext`, подтверждение действий, адаптеры корпоративных сервисов. |
| `ai` (Python, FastAPI) | индекс KB в памяти | Доступен только из сети backend. Ходит в LLM-шлюз и в Confluence (если `KB_SOURCE=confluence`). |
| PostgreSQL | stateful | Пользователи, чек-листы, прогресс, разговоры, заявки, вопросы наставнику. Бэкапы по стандарту компании. |

Модель эмбеддингов (`intfloat/multilingual-e5-small`, ONNX, CPU) запекается в образ `ai` при сборке, поэтому в рантайме сервису не нужен доступ к Hugging Face (`HF_HUB_OFFLINE=1`). GPU не нужен.

## 2. Переменные окружения

### LLM

| Переменная | Прод-значение | Зачем |
|---|---|---|
| `LLM_PROVIDER` | `openai_compatible` | Один адаптер под любой Chat Completions API. |
| `LLM_BASE_URL` | адрес корпоративного LLM-шлюза, например `https://llm-gateway.internal/v1` | Через шлюз идут учёт токенов, лимиты, аудит и маскирование. Подойдёт и self-hosted vLLM. |
| `LLM_API_KEY` | ключ сервиса из секрет-хранилища (Vault / k8s Secret) | Только через окружение: в образе и в репозитории ключа нет. |
| `LLM_MODEL` | модель с поддержкой tools и streaming | Проверено на `openai/gpt-6.1-terra`. Перед сменой модели прогоняется eval (раздел 7). |
| `LLM_EXTRA_BODY` | например `{"reasoning":{"effort":"low"}}` | Параметры конкретного провайдера. |
| `LLM_TIMEOUT_SECONDS` / `LLM_FIRST_BYTE_TIMEOUT_SECONDS` | 60 / 15 | UI не зависает: при тайм-ауте приходит событие `error`, и пользователь видит «Повторить». |

### Поиск и база знаний

| Переменная | Прод-значение | Зачем |
|---|---|---|
| `RAG_MODE` | `hybrid` | BM25 + эмбеддинги (RRF). `bm25` — запасной режим без модели. |
| `RAG_EMBEDDING_MODEL` | build-arg образа, по умолчанию `intfloat/multilingual-e5-small` | Модель меняется пересборкой: `docker build --build-arg RAG_EMBEDDING_MODEL=...`. После замены — eval. |
| `RAG_TOP_K` / `RAG_MIN_SCORE` | 4 / 0.2 | Сколько фрагментов видит модель. |
| `KB_SOURCE` | `confluence` | Источник базы знаний. |
| `CONFLUENCE_URL` | `https://confluence.internal` | Confluence Server / Data Center. |
| `CONFLUENCE_TOKEN` | personal access token **сервисной учётки с правом только на чтение** | Передаётся как `Bearer`. Учётке открыто только пространство онбординга. |
| `CONFLUENCE_SPACE` | ключ пространства, например `ONBOARD` | Бот знает только то, что лежит в этом пространстве. |
| `KB_RELOAD_SECONDS` | `3600` | Периодически перечитывает Confluence. Ручная перезагрузка — `POST /v1/kb/reload` (через backend, только для администратора KB). |
| `KB_STALE_DAYS` | 180–365 | Порог «устаревшего» документа для lint. |
| `KB_LINT_MAX_LLM_CALLS` | 15–50 | Бюджет LLM-проверки противоречий за один прогон. |

### Backend и вход

| Переменная | Прод-значение |
|---|---|
| `JWT_SECRET` | случайная строка ≥ 32 символов из секрет-хранилища |
| `DB_*` | учётка PostgreSQL с минимальными правами |

**SSO — следующий шаг.** Сейчас вход локальный (email + пароль → JWT). В компании backend становится OIDC-клиентом корпоративного IdP (Keycloak / ADFS): роль (`intern` / `buddy`), команду и наставника берём из claims или HR-системы, а не из формы регистрации. AI-сервис это не затрагивает: он не аутентифицирует пользователей, а получает уже проверенный `UserContext` от backend.

## 3. Потоки данных и что уходит за периметр

```text
Браузер / расширение ──HTTPS──> backend ──> PostgreSQL
                                  │
                                  └──> ai ──> Confluence (внутри периметра, только чтение)
                                        ├──> эмбеддинги: локально, CPU, наружу ничего не уходит
                                        └──> LLM-шлюз ──> LLM-провайдер  ← единственный выход
```

Что получает LLM при каждом вызове:

| Данные | Чат | Черновик наставнику | Gaps / KB lint |
|---|---|---|---|
| Фиксированный системный промпт | да | да | да |
| Фрагменты KB (top-k) | да | да | пары фрагментов (lint) |
| Сообщение и до 20 реплик истории | да | вопрос стажёра | тексты вопросов (только для названий кластеров) |
| `UserContext`: имя, роль, профессия, команда, наставник, этап, задачи, открытые заявки | да | без имени и задач: роль, профессия, команда, этап | нет |

Чего LLM **не получает**: паролей, JWT, данных других сотрудников, сведений, которые backend не включил в `UserContext` пользователя. RBAC выполняет backend, а промпт защитой не считается.

Как сократить то, что уходит наружу:

1. **Лучший вариант — модель внутри периметра** (vLLM / корпоративный шлюз к self-hosted модели). Тогда за периметр не уходит ничего.
2. Если провайдер внешний: договор об обработке данных, отключённое хранение и обучение на запросах (zero retention), шлюз с маскированием ПДн.
3. Минимизация на стороне backend: не передавать `display_name` и `buddy_name`, если продукт без них обходится.

Логи: только метаданные (латентность, токены, вызванные инструменты, `finish_reason`). Тексты сообщений и ПДн в логи не пишутся. Разговоры хранятся в PostgreSQL, срок хранения задаётся политикой компании.

## 4. Масштабирование

- **AI stateless**, кроме индекса KB в памяти. Масштабируется репликами за внутренним балансировщиком. Каждая реплика держит свою копию индекса и сама перечитывает Confluence (`KB_RELOAD_SECONDS`). Один uvicorn-воркер на контейнер: каждый воркер загружает модель эмбеддингов (~0.5 ГБ RAM), поэтому выгоднее больше контейнеров.
- **Узкое место — LLM**, а не наш код. Лимиты задаёт шлюз. Backend отдаёт клиенту `rate_limited`, UI показывает статус ожидания.
- **Рост KB.** Сейчас поиск по эмбеддингам — полный перебор в памяти. Этого хватает на сотни страниц (тысячи фрагментов). Когда фрагментов десятки тысяч (весь Confluence, а не пространство онбординга), переходим на **pgvector** в уже имеющемся PostgreSQL:
  - таблица `kb_chunks(id, doc_id, title, url, updated, text, embedding vector(384))` с индексом HNSW и полнотекстовым `tsvector` для лексической части;
  - индексация — отдельный job (`reload` превращается в инкрементальную загрузку изменённых страниц по `version.when`), реплики AI перестают держать индекс в памяти;
  - интерфейс `Retriever.search()` не меняется, поэтому промпты, eval и API остаются прежними.
- **Права на документы.** Сейчас вся KB считается доступной любому стажёру, поэтому подключаем одно пространство онбординга. Если понадобятся закрытые разделы, у фрагментов появляется метка доступа, а ретривер фильтрует их по ролям из `UserContext` до передачи в LLM.

## 5. Метрики и мониторинг

| Что | Где | Алерт |
|---|---|---|
| Доступность | `GET /health` у backend и ai (healthcheck в compose / k8s probes) | сервис недоступен > 1 мин |
| Ошибки LLM | логи `ai.agent`: `llm error code=…` | доля `error` > 5% за 15 мин |
| Латентность | `latency_ms` в событии `done` и в логах | p95 до первого токена > 3 с |
| Стоимость | `usage.input_tokens / output_tokens` | расход выше бюджета дня |
| Качество | `GET /api/metrics/chat`: deflection rate, 👍/👎, доля `no_answer` | рост `no_answer` или 👎 неделя к неделе |
| Свежесть KB | `GET /v1/kb/lint` / CLI `python -m app.kb_lint` — еженедельный отчёт владельцам KB | новые противоречия |
| Пробелы KB | `POST /v1/analytics/gaps` по эскалированным вопросам — ежемесячно | крупные кластеры без статьи |
| Перезагрузка KB | логи `ai.sources`: `kb reloaded` / `reload failed` | 3 неудачи подряд |

Следующий шаг — экспорт этих метрик в Prometheus / Grafana компании. Сейчас они доступны в логах и через API.

## 6. Чек-лист безопасности

- [ ] AI-сервис не опубликован наружу: доступ только из сети backend (network policy).
- [ ] Секреты (`LLM_API_KEY`, `CONFLUENCE_TOKEN`, `JWT_SECRET`, `DB_PASSWORD`) лежат в секрет-хранилище. `.env` в репозитории нет.
- [ ] Учётка Confluence только на чтение и только на пространство онбординга.
- [ ] RBAC в backend: стажёр не видит чужие заявки и вопросы, `allowed_actions` и уровни доступа считает backend. Подтверждение действия повторно проверяет права.
- [ ] Действия только через «предложить → подтвердить»: AI ничего не выполняет сам.
- [ ] Prompt injection: текст KB, страниц (расширение) и сообщений — данные. Системный промпт и инструменты фиксированы. Набор injection-кейсов из eval проходит.
- [ ] `POST /v1/kb/reload`, `GET /v1/kb/lint` и `POST /v1/analytics/gaps` доступны только ролям администратора KB / HR через backend.
- [ ] В логах нет текстов сообщений и ПДн (проверить выборку логов перед запуском).
- [ ] С LLM-провайдером подписан DPA, хранение запросов выключено (или модель внутри периметра).
- [ ] Чувствительные сценарии (ПДн, финансы) не подключены.
- [ ] Rate limit на чат на уровне backend / шлюза.

## 7. Eval перед выкатом

Перед выкатом и после каждой смены модели, промпта, ретривера или источника KB:

1. **Свой датасет.** 50–100 реальных вопросов стажёров из прошлых потоков. К каждому — ожидаемый документ Confluence и поведение: ответ, отказ («в базе нет»), действие, противоречие. Формат — как `apps/ai/eval/dataset.jsonl`. Отдельно отложенная выборка (holdout), на которой промпты не подбираются.
2. **Прогон:** `python -m eval.run retrieval` (без LLM, recall@k) и `python -m eval.run e2e` (полный ход агента через шлюз).
3. **Пороги выката** (из SDD-002, раздел 7): recall@4 ≥ 0.9, корректный источник ≥ 0.9, корректность отказа ≥ 0.9, точность действий ≥ 0.9, p95 до первого токена ≤ 3 с.
4. **KB lint** на корпоративном пространстве: противоречия и устаревшие документы разбирают владельцы KB до запуска, иначе бот будет честно говорить «документы расходятся» слишком часто.
5. **Пилот:** одна команда или один поток стажёров, затем A/B против контрольной группы. Сравниваем время до первой самостоятельной задачи, число обращений к наставнику и долю вопросов, закрытых без наставника.

## 8. Порядок внедрения

1. Развернуть стенд во внутреннем контуре с `LLM_PROVIDER=mock`: проверить вход, чек-листы и действия без LLM.
2. Подключить LLM-шлюз и Confluence (`KB_SOURCE=confluence`), прогнать KB lint и eval на своём датасете.
3. Заменить mock-адаптеры заявок (отгул, доступ) на реальные API HR- и IDM-систем в backend. Схема «предложить → подтвердить → выполнить» и контракт не меняются.
4. Подключить SSO.
5. Пилот на одной команде, мониторинг по разделу 5, еженедельный разбор gaps и lint с владельцами KB.
