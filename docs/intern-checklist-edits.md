# Чек-лист стажёра: правки руководителя, доработка, демо-завершение

Краткое описание решений бэкенда (миграция `00007_intern_checklist_edits.sql`). Контракт — `contracts/backend.openapi.json`.

## Модель

- Каталог (`checklist_items` с `assigned_user_id IS NULL`) общий для всех стажёров и **не меняется** правками руководителя.
- У каждого стажёра есть собственные строки `user_checklist_progress` — это и есть «копия» чек-листа стажёра. Миграция 00007 добавляет в них:
  - `hidden_at` — задача убрана из чек-листа этого стажёра (мягкое удаление: отправки, комментарии и подсказки сохраняются);
  - `title_override`, `description_override`, `expected_result_override`, `estimated_minutes_override`, `due_at_override` — формулировка, оценка и срок для этого стажёра; `NULL` означает значение каталога.
- Личные задачи — как и раньше, `checklist_items` с `assigned_user_id = стажёр`; теперь их можно добавлять и в общий чек-лист (`checklist_type`).
- Все переходы статусов читают задачи через `ChecklistRepository.GetItemsForUser`, где применяются overrides и отфильтрованы скрытые задачи. Поэтому скрытая задача не учитывается в процентах, в отзыве о чек-листе, в подсказках, в контексте AI и в очереди ревью наставника.
- Если убрана текущая (активная) задача каталога, становится активной первая незавершённая видимая задача — стажёр не «застревает».

Почему так: миграция только добавляет nullable-колонки, существующие данные и запросы работают как раньше; не нужно копировать каталог на каждого стажёра и переносить внешние ключи отправок/комментариев.
Альтернатива — полная копия чек-листа на стажёра (`checklist_items` на каждого) — дала бы произвольную структуру этапов, но потребовала бы миграции данных и правок всех запросов; для MVP избыточна.

Не реализовано: перестановка задач, смена `requires_review`, сброс override к значению каталога, восстановление удалённой задачи, список удалённых задач.

## Права (проверяет бэкенд, не LLM)

| Действие | Стажёр | Наставник (buddy) | Руководитель (teamlead) |
|---|---|---|---|
| Видеть оба чек-листа стажёра (`GET /api/staff/interns/{id}/progress`) | — | свой стажёр | свой стажёр (теперь и общий чек-лист) |
| История ревью задачи (`GET /api/staff/interns/{id}/checklist-items/{itemId}/submissions`) | своя — `GET /api/checklist-items/{itemId}/submissions` | свой стажёр | свой стажёр, только чтение |
| Принять / вернуть на доработку (`POST /api/buddy/submissions/{id}/review`) | — | свой стажёр | **403** |
| Добавить / изменить / убрать задачу стажёра | — | 403 | свой стажёр |
| Демо: завершить чек-листы на 100% | только с `ADMIN_OPEN_FOR_ALL=1` | только с `ADMIN_OPEN_FOR_ALL=1` | любой стажёр (админ-панель) |

«Свой стажёр»: `users.buddy_id` / `users.teamlead_id` равен id пользователя; иначе 404 (как в остальных staff-маршрутах).

## Маркер доработки

`ChecklistItem.returned_for_rework = true`, если последняя отправка задачи отклонена наставником, а новая ещё не отправлена (статус задачи снова `active`, колонка «Активно»). `rework_comment` — комментарий наставника. После повторной отправки маркер снимается.

## Демо-завершение

`POST /api/admin/accounts/{userID}/complete-checklists` — только для демонстрации: все видимые задачи текущих чек-листов стажёра становятся `completed` (задачи с ревью — `verified`), ожидающие отправки одобряются от имени наставника стажёра с комментарием «Демо: …». Повторный вызов ничего не меняет.
