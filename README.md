# AI-Buddy

AI-Buddy — демо адаптации стажёров. Go Backend хранит пользователей, чек-листы и прогресс, проверяет результаты с buddy, обрабатывает персональные задачи teamlead, заметки, календарь, корпоративные mock-заявки, feedback и подсказки. Учётные записи и назначения поступают из синтетического Mock HR. Backend обращается к отдельному AI-сервису по HTTP для чата и подсказок; реализация AI/ML здесь не оценивается.

Web обращается к backend через `/api`. В текущей сборке стажёру доступен интерфейс адаптации, а buddy и teamlead видят временную страницу с кнопкой выхода; их серверные API работают независимо от этого ограничения Web. Подробные правила и маршруты: [SDD](docs/SDD.md), [Backend OpenAPI](contracts/backend.openapi.json), [отчёт о тестировании](docs/testing/backend-test-report.md).

## Стек и требования

| Часть | Версия или источник |
|---|---|
| Go Backend | Go 1.26.0 (`apps/backend/go.mod`, образ `golang:1.26-alpine`); pgx/v5 5.12.0, golang-jwt/jwt/v5 5.3.1 |
| Данные | PostgreSQL 16 (`postgres:16-alpine`), миграции Goose v1 |
| Goose CLI | CI устанавливает v3.24.1; подтверждённые локальные проверки использовали v3.30.1 |
| Запуск Compose | Docker Desktop с `docker compose` и поддержкой `--wait`; в проверенном окружении Docker Engine 29.9.2, Compose 5.6.1 |
| Web-сборка | Node.js 22 (`node:22-alpine`); React 19.1.0, TypeScript 5.8.3, Vite 6.4.6 по `apps/web/package.json` |
| AI-контейнер | Python 3.12 (`apps/ai/Dockerfile`); для backend важны только контракты `/chat` и `/hint` |

Основной терминал на Windows — **Git Bash**. Нужны Docker Desktop, Go 1.26, Goose в `PATH` и доступный `powershell.exe`; сам обязательный bootstrap остаётся PowerShell-скриптом. Node.js и Python нужны только для локальных JS/контрактных проверок: Compose собирает Web и AI сам. Порты по умолчанию: Web `127.0.0.1:5173`, Backend `127.0.0.1:8080`, PostgreSQL `127.0.0.1:5433`.

## Первый запуск через обязательный bootstrap

Из корня репозитория в Git Bash:

```bash
cp .env.example .env
# Замените DB_PASSWORD и JWT_SECRET в .env на свои случайные значения.
# JWT_SECRET должен содержать не менее 32 символов.
go install github.com/pressly/goose/v3/cmd/goose@v3.24.1
export PATH="$(go env GOPATH)/bin:$PATH"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ./scripts/bootstrap.ps1
docker compose -p ai-buddy ps
```

`scripts/bootstrap.ps1` — обязательная точка первоначального развёртывания. Он запускает PostgreSQL, проверяет историю миграций (допустима любая версия от 1 до последней в `apps/backend/migrations`) и применяет недостающие миграции через Goose. Затем `cmd/init-catalog` загружает общий и профессиональные чек-листы из `apps/backend/scripts`, `cmd/sync-hr` синхронизирует `data/corporate_employees.json`, а Compose собирает и запускает AI, backend и Web с ожиданием healthcheck. Скрипт не преобразует старую несовместимую схему, не очищает БД и не сбрасывает данные. Нужен свободный набор портов; их можно изменить в `.env`. Для независимого стенда у bootstrap есть параметры `-ProjectName`, `-EnvFile`, `-CredentialsDirectory`.

Откройте <http://127.0.0.1:5173>. Проверки из Git Bash: `curl -i http://127.0.0.1:8080/health` возвращает liveness процесса, а `curl -i http://127.0.0.1:8080/ready` возвращает 200 только при доступной PostgreSQL, актуальной версии всех Goose-миграций и непустом каталоге. При неполной подготовке `/ready` возвращает 503. Поэтому прямой `docker compose up` на пустой БД не является заменой bootstrap: сначала выполните `powershell.exe -NoProfile -ExecutionPolicy Bypass -File ./scripts/bootstrap.ps1`.

Для повторного запуска уже подготовленной и мигрированной БД допустим `docker compose -p ai-buddy up -d --build --wait`; он сам не применяет миграции, не инициализирует каталог и не запускает Mock HR Sync. После новых миграций или изменения синтетического HR-снимка снова запускайте bootstrap. Остановка без удаления PostgreSQL volume: `docker compose -p ai-buddy stop`. Не используйте `docker compose down -v`, если данные нужно сохранить.

PostgreSQL integration tests используют только отдельный временный контейнер с `tmpfs` и не читают `.env` приложения:

```bash
bash scripts/test-backend-postgres.sh
```

Никогда не подставляйте рабочий DSN в `TEST_DATABASE_URL` и не запускайте тесты против Compose-БД. Подробности: [инструкция PostgreSQL-тестов](docs/testing/postgres-integration-git-bash.md).

## Тестовые учётные записи

`data/corporate_employees.json` содержит следующие **синтетические** email. Паролей в этом файле нет.

| Роль | Email |
|---|---|
| Стажёр Backend | `backend.intern@demo.example` |
| Стажёр Frontend | `frontend.intern@demo.example` |
| Стажёр ML | `ml.intern@demo.example` |
| Ещё один стажёр ML | `ml.other@demo.example` |
| Buddy | `buddy@demo.example` |
| Teamlead | `teamlead@demo.example` |

При первой синхронизации `cmd/sync-hr` генерирует случайный пароль для каждого нового пользователя. Bootstrap выводит **путь** к приватному файлу `secrets/hr-*.json`, но не пароли. Откройте файл локально и используйте запись нужного email для входа. `secrets/` исключён из Git и Docker build context; не публикуйте файл. Повторный sync сохраняет пароли, ID и прогресс существующих пользователей и создаёт новый файл только с паролями новых записей (при их отсутствии — `[]`). Поэтому сохраните файл **первого** запуска: последующий пустой файл не восстановит старые пароли. Для browser E2E и live-проверки контрактов укажите путь к первому файлу в `E2E_CREDENTIALS_FILE`.

## Порядок проверки Backend MVP

1. Войдите как `backend.intern@demo.example` с паролем из приватного файла. `POST /api/auth/login` выдаёт access/refresh token; `GET /api/auth/me` возвращает роль и назначения. Logout требует оба токена; повторный refresh старым токеном запрещён.
2. Получите `GET /api/checklists` и `GET /api/progress`. Доступны общий и Backend-трек. Обычные задачи открываются последовательно внутри каждого чек-листа; треки независимы.
3. Завершите активную задачу без проверки через `POST /api/checklist-items/{itemID}/complete`. Задачу с `requires_review` сдайте через `POST /api/checklist-items/{itemID}/submissions`. До одобрения buddy она не повышает подтверждённый процент; после одобрения — повышает. API buddy: `GET /api/buddy/submissions`, `POST /api/buddy/submissions/{submissionID}/review`.
4. Проверьте `GET/POST /api/notes` и `/api/calendar/events`; чтение, изменение и удаление по ID доступны только владельцу. Teamlead может добавить назначенному стажёру персональную задачу через `POST /api/teamlead/interns/{internID}/checklist-items`; она сразу `active` и не меняет статусы других задач.
5. Проверьте `GET /api/corporate/me`, `/api/corporate/tools` и `POST /api/corporate/access-requests` с явным подтверждением и ключом идемпотентности. После завершения всего чек-листа доступен `POST /api/checklists/{checklistID}/feedback`.
6. `POST /api/chat` отправляет вопрос в AI `/chat`; hint worker использует AI `/hint`. Backend возвращает `502` при ошибке чата, а для подсказок применяет повторные попытки и fallback. Эти запросы не доказывают качество ML.

Маршруты, JSON-тела и ограничения ролей приведены в [Backend OpenAPI](contracts/backend.openapi.json) и [SDD](docs/SDD.md). В текущем Web buddy/teamlead видят заглушку с Logout; их сценарии проверяйте через API или автоматические Go-тесты.

## Тесты Backend

Ручной `PUT /api/buddy/interns/{internID}/teamlead` удалён. На существующей нагрузочной БД v9 миграционный контейнер проверяет схему и не применяет новую историю; чистая нагрузочная БД получает v1. Рабочий нагрузочный стенд сейчас находится на v8: его данные не менялись, а новый запуск с этой кодовой базой безопасно остановится. Обновление до v9 разрешено **позже отдельной операцией** после backup и согласования окна. Не направляйте демо и тестовые команды на рабочее нагрузочное окружение.

## AI-ассистент (apps/ai)

AI-сервис доступен только внутри Docker-сети, клиенты ходят в него через Backend. Без ключа он работает в детерминированном режиме `LLM_PROVIDER=mock`. Для настоящих ответов задайте в `.env` переменные `LLM_PROVIDER=openai_compatible`, `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`. Проверено с OpenRouter и моделью `openai/gpt-6.1-terra`. Остальные переменные с комментариями описаны в `.env.example`. Спецификация: `docs/specifications/002-ai-agent-chat.md`. Eval: `apps/ai/eval/`.

Backend реализует API ассистента из `contracts/backend.openapi.json`. Код: `apps/backend/internal/service/assistant.go`, таблицы — в миграции `00002_assistant.sql`.

- `POST /api/chat/stream` и `/api/chat/brief/stream` — ответ потоком (SSE). Backend собирает контекст стажёра из БД: задачи, этап, наставника, заявки — и хранит историю диалога.
- `/api/actions/{id}/confirm|cancel` — действие выполняется только после подтверждения стажёром.
- `/api/requests` — мок-заявки на отгул и доступ. Согласует их только руководитель: `GET /api/buddy/requests` (список) и `POST /api/buddy/requests/{id}/decision` (решение с необязательным `comment`, миграция `00004`). В вебе «Согласовать» открывает заявку в демо-портале `/portal/requests/...` с полем комментария.
- `/api/buddy/questions` — вопросы, переданные наставнику, с AI-черновиком ответа. Видит и отвечает только наставник, руководитель их не видит.
- `/api/metrics/chat` — метрики эффекта для наставника. Качество базы знаний (`/api/admin/kb/gaps`, `/api/admin/kb/lint`) перенесено в админку.
- `POST /api/requests` — заявка из формы в окне Бади (те же проверки и политика, что у подтверждённого действия; admin стажёрам не выдаётся).
- `POST /api/auth/link` — отдельная сессия того же пользователя для второго клиента (расширения), по refresh-токену вызывающего без ротации.
- `POST /api/questions` — вопрос наставнику из вкладки «Вопросы наставнику» без чата.
- `GET /api/suggestions` и `POST /api/chat/hint` — подсказки в пустом поле ввода: готовый вопрос из `data/suggestions.json` отвечает выдержкой из документа и ссылкой **без вызова модели**, текст собирает backend. Любое следующее сообщение идёт в модель, подсказка попадает в историю диалога.
- `/api/kb/docs/{id}` — документ базы знаний целиком: источник из ответа открывается прямо в окне Бади.

**Бади на сайте и в расширении — один виджет** (`apps/extension/buddy/widget.js`, связь с backend — `apps/extension/lib/gateway.js`). Сайт подключает его через alias `@buddy`; если расширение установлено, на сайте работает Бади из расширения, а сайт передаёт ему свои подсказки. У окна два режима: компактный рядом с персонажем и большой, всегда по центру экрана (⤢/⤡); размер каждого меняется за угол и запоминается в браузере. В большом режиме есть вкладки «Чат», «Вопросы наставнику», «Заявки», «Заметки» и «Календарь»: вопросы наставнику, заявки на отгул, отпуск и доступ, заметки и события можно смотреть и создавать прямо в окне (`POST /api/requests`, форма — явное подтверждение). Если расширение не установлено, встроенный Бади на сайте показывает знак «⚠ Нет расширения»; по клику в чате появляется инструкция со ссылкой на страницу-заглушку `/install-extension.html` (`apps/web/public/`). Источники под ответом спрятаны за кнопкой «Источники · N»; клик по источнику открывает документ в окне. Если для действия не хватает данных, бот не расспрашивает текстом, а рисует **форму** прямо в чате (отгул или отпуск, доступ, заметка, событие в календаре, вопрос наставнику). Известные поля он подставляет сам, стажёр правит остальное и жмёт «Отправить». Модель получает для этого инструмент `show_form` (`apps/ai/app/forms.py`): список форм ограничен разрешёнными пользователю действиями, значения полей проверяются, а запись создаёт тот же backend с теми же проверками, что и для карточки подтверждения. Если данных хватает, по-прежнему показывается карточка «Подтвердить / Отменить». Пока пользователь не вошёл, окно целиком занимает форма входа. Единый вход: вошли на сайте или в боте — вошли и там и там, выход тоже общий. У сайта и расширения отдельные сессии одного пользователя (`POST /api/auth/link`), вход сохраняется между перезапусками браузера: короткий access-токен обновляется по refresh-токену с ротацией, обновление идёт под Web Lock, чтобы вкладки не ломали друг другу ротацию (`apps/extension/lib/auth.js`, `lib/sso.js`). Сайт один для всех ролей и построен по макетам: у стажёра разделы «Главная», «Календарь», «Задачи» и «Бади», у наставника — «Главная», «Команда», «Вопросы» и «Календарь», у руководителя — «Главная», «Команда», «Заявки» и «Календарь». Отдельной страницы «Бади» нет: описание помощника лежит в демо-вики (`/wiki/buddy.html`). Профиль и заметки открываются вкладками справа; заметки (список, создание, правка, удаление) общие с вкладкой «Заметки» окна Бади.

**Корпоративные демо-сервисы в одном стиле:** портал заявок (`/portal/requests`) и база знаний (`/wiki/`) используют общую «корпоративную» шапку и оформление. **Демо-вики** `http://127.0.0.1:5173/wiki/` собирается из `data/kb` при сборке веба (`apps/web/scripts/build-wiki.mjs`). Ссылки на источники ведут туда (`KB_WIKI_URL`), кнопка «Открыть документ полностью» подсвечивает процитированный фрагмент.

Фоновые подсказки «застрял на задаче» (`task_hints`) генерирует AI-эндпоинт `/hint`.

Демо-страницы «рабочих инструментов» для персонажа расширения: <http://127.0.0.1:5173/demo/wiki.html>, `/demo/grafana.html`, `/demo/jira.html` (статика в `apps/web/public/demo/`, данные синтетические).

Ручная проверка описана в `docs/manual-testing.md`.

## Расширение Chrome (apps/extension)

```bash
export BACKEND_ORIGIN='http://127.0.0.1:8080'   # адрес Backend (BACKEND_PORT)
npm run build --workspace @ai-buddy/extension
```

В Chrome 116+ откройте `chrome://extensions`, включите режим разработчика, нажмите «Загрузить распакованное расширение» и выберите `apps/extension/dist`. На каждой странице (кроме самого веб-приложения, где есть свой виджет) в правом нижнем углу появляется персонаж Бади. Клик по нему или по иконке расширения открывает окно чата (на служебных страницах Chrome, где скрипты расширений запрещены, кнопка лишь включает показ Бади и ставит на иконку значок «✓»: он появится на ближайшей обычной странице): ответ приходит потоком, у ответов есть источники, у действий — карточки подтверждения. Бади можно перетаскивать, он даёт подсказки по открытой странице. Окно чата всегда открывается компактным; кнопка ⤢ делает его большим. Подробности описаны в [apps/extension/README.md](apps/extension/README.md).

## Админ-панель (руководитель)

Админка открывается по адресу `http://127.0.0.1:5173/admin` (пункта в меню нет). Руководителю (`teamlead@demo.example`) она доступна всегда, все маршруты `/api/admin/*` на бэкенде закрыты ролью `teamlead` (наставник и стажёр получают 403). Для демо-записи видео есть флаг `ADMIN_OPEN_FOR_ALL=1` в `.env`: тогда панель открыта всем ролям (`GET /api/admin/access` сообщает вебу, пускать ли на страницу). По умолчанию флаг выключен. Шесть вкладок:

- **Аккаунты** — все пользователи с ролью, профессией, командой, наставником и руководителем, датой входа и числом активных сессий; фильтр по роли. Хэши паролей и токены не отдаются.
- **API и модель** — провайдер, модель, режим (mock или llm), для OpenRouter ещё баланс ключа (`GET {LLM_BASE_URL}/key`), дневной бюджет токенов и кнопка «Проверить модель» (короткий запрос с теми же настройками, что у чата). Ключ остаётся в AI-сервисе.
- **Оповещения** — каталог всплывашек Бади: откуда берётся, когда срабатывает, как часто, пример текста. «Проверить» показывает пример в вашем Бади; для «Задача идёт дольше плана» запускает настоящий тик воркера подсказок и показывает результат.
- **Оценки ответов** — счётчики 👍/👎 стажёров и комментарии, оставленные под 👎 («что не так с ответом»). Наставники эти оценки не видят (`GET /api/admin/feedback`, колонка `chat_messages.feedback_comment`, миграция `00003`).
- **База знаний** — «Пробелы» (темы вопросов, на которые бот не нашёл ответ) и «Линтер» (противоречия и устаревшие документы).
- **Система** — проверки базы данных, AI-сервиса, базы знаний и воркера подсказок, счётчики, кнопка «Перечитать базу знаний».

Контракт: `/api/admin/*` в `contracts/backend.openapi.json`, `/v1/admin/*` в `contracts/ai.openapi.json`.

## Проверки
Команды ниже выполняются из корня репозитория в Git Bash. Без `TEST_DATABASE_URL` Go запускает доступные unit/handler-тесты; PostgreSQL integration-тесты пропускаются. Не направляйте тестовые переменные на БД приложения или нагрузочный стенд.

```bash
cd apps/backend
go test -p 1 -count=1 ./...
go vet ./...
cd ../..
```

Полный integration/E2E запускается готовым безопасным сценарием. Он создаёт отдельный PostgreSQL с `tmpfs`, применяет актуальные миграции, включает `RUN_E2E=1` и гарантированно останавливает контейнер:

```bash
bash scripts/test-backend-postgres.sh
```

Тест `TestOpenPostgresLive` имеет отдельный opt-in флаг `VERIFY_DATABASE_CONNECTION=1` и переменные `DB_*`; приведённый безопасный прогон его не включает. Для воспроизведения **точного** результата покрытия 81,19% использовались Go 1.26.0 в Linux-контейнере, `RUN_E2E=1`, отдельные базы и команда `go test -p 1 -count=1 -coverpkg=./... -coverprofile=coverage.out ./...`; детали окружения и результаты — в [отчёте](docs/testing/backend-test-report.md). Race detector требует Linux/CGO/GCC; ранее подтверждённый прогон приведён там же.

- `apps/backend` — API, команды, миграция и SQL справочников.
- `apps/web`, `apps/extension`, `apps/ai` — Web, Chrome MV3 и AI-сервис.
- `packages/client` — клиент Backend API; `contracts` — OpenAPI.
- `ops/load` — нагрузка и мониторинг.
- `data/corporate_employees.json` — Mock HR без паролей.

## Проверка контрактов и Web-сборки

Для статической проверки двух OpenAPI-спецификаций нужны `jsonschema` и `openapi-spec-validator` в изолированном Python-окружении. Следующие версии прошли проверку на Python 3.13.15:

```bash
py -3 -m venv .venv
./.venv/Scripts/python.exe -m pip install 'jsonschema==4.26.0' 'openapi-spec-validator==0.9.0'
./.venv/Scripts/python.exe scripts/check_contracts.py
```

Для live-проверки запустите Compose и используйте первый файл учётных данных Mock HR, содержащий `buddy@demo.example`:

```bash
export E2E_CREDENTIALS_FILE='C:/absolute/path/to/first-hr-sync.json'
export CHECK_LIVE=1
./.venv/Scripts/python.exe scripts/check_contracts.py
unset CHECK_LIVE
```

Web, Extension и общий JS-клиент проверяются из корня репозитория командами `npm ci`, `npm test`, `npm run build`. Browser E2E (`npm run test:e2e`) дополнительно требует работающий Compose, `E2E_CREDENTIALS_FILE` и установленный Chromium для Playwright.

## Известные ограничения и материалы

- Mock HR и корпоративные заявки — синтетические данные; связи с реальными системами нет. После ручного `sync-hr` backend требует пересборки/перезапуска для нового снимка.
- `/health` отражает только liveness. Подсказка генерируется асинхронно и может появиться не сразу. AI/ML качество этим репозиторием Backend не подтверждается.
- Финальный измеренный показатель — **81,19% statement coverage Go backend** при `-coverpkg=./...`, включая opt-in E2E; это не покрытие Web, AI или всего проекта.
- Исходники, SDD, тесты и [отчёт о тестировании](docs/testing/backend-test-report.md) входят в материалы сдачи. Сырые логи и HTML-отчёт лежат локально в игнорируемом `test-results/` и не должны добавляться в Git целиком. Приватный `инфа.md`, `.env` и `secrets/` не публикуются.
