## Диагностика read / 50 VU, 14.11.2026

Серия `ai-buddy-load` была остановлена на `read-20261114-003231-598b3e8d` после `POST /api/auth/login: EOF` и `HTTP 0`. Этот запуск имеет частичные `summary.json`, `metrics.ndjson`, `manifest.json`, но не является завершённым трёхминутным измерением: summary содержит всего 57 HTTP-запросов, из них 2 workload с p95 около 71 s и HTTP error rate 100%. Они не включаются в сравнительную таблицу. Четыре предыдущих полных результата в `load-results/` не изменены. Снимок Prometheus за окно сбоя сохранён в `load-results/diagnostics-20261114/read50-failure-prometheus.json`.

**Установленный механизм перегрузки:** каждый вызов `VerifyPassword` запускал Argon2id с параметром `m=65536` KiB (64 MiB), без ограничения одновременности. Все 50 VU начинали работу с логина, то есть потенциально требовали около 3.2 GiB только для рабочих буферов Argon2id. Prometheus зафиксировал пик `go_memstats_heap_alloc` 3207 MiB, RSS backend 2561 MiB и CPU 6.1 cores в окне сбоя; Docker VM сообщала лимит около 3.528 GiB для контейнеров. Это убедительно объясняет давление на память и задержки логина. Непосредственную причину ответа Docker Engine `unexpected EOF` / exit 125 установить отдельно нельзя: не сохранилось точной хостовой телеметрии на этот момент. Backend и PostgreSQL после сбоя были healthy, `OOMKilled=false`, перезапусков не было.

Большой `go_memstats_heap_sys` после нагрузки сам по себе не является утечкой. До обновления backend, после теста `heap_alloc` был около 4 MiB, `heap_released` около 3961 MiB, RSS процесса около 45 MiB; cgroup `memory.current` около 67 MiB (`anon` около 43 MiB, `file` около 19 MiB). Значение Docker stats около 1 GiB сразу после теста относилось к ранее выделенной памяти до её возврата/выгрузки и не характеризует живой heap. Счётчики `memory.stat` показывают активное сканирование и swap за всё время жизни cgroup, но без исходного снимка их нельзя приписать только аварийному прогону.

В `internal/security/password.go` введён общий лимит четыре одновременные операции Argon2id для создания и проверки хеша. Ожидаемая рабочая память активных Argon2id ограничена примерно 256 MiB; ожидающие проверки с отменённым HTTP-контекстом прекращаются. Алгоритм, параметры хеша и ответ API не изменены. Добавлен тест отмены при занятых слотах. В `ops/load/run-k6.ps1` теперь сохраняется полный `k6-console.txt` нового запуска. `ops/load/run-series.ps1 -Resume` проверяет четыре завершённых отчёта, их baseline и файлы, пропускает их и не принимает частичный пятый. Изменение кода блокирует возобновление без явного `-AllowChangedConfig`; с этим флагом старые и новые результаты помечаются как разные когорты. `-MaxRuns 1` позволяет выполнить только один следующий прогон.

Проверки: `go test ./...`, `go vet ./...`, `docker compose ... config --quiet`, PowerShell-синтаксис и dry-run `run-series.ps1 -Resume -AllowChangedConfig -MaxRuns 1` прошли. Для Go команд понадобился `GOCACHE` внутри workspace из-за отказа доступа к обычному Windows cache; сообщение Go telemetry не повлияло на код возврата. Пересобран и обновлён только backend `ai-buddy-load`; базовые данные проверены: `current_database()=ai_buddy_load`, 100 пользователей, 0 заметок и 0 событий. Prometheus target `UP`, Grafana доступна.

После изменения выполнены только короткие диагностические read-прогоны: 2 VU / 30s (`read-20261114-010722-ba5ab081`) — 1136 workload-запросов, 0% ошибок, 100% checks, p95 3.52 ms; 10 VU / 30s (`read-20261114-010805-4a3ffc5c`) — 5604 запросов, 0% ошибок, 100% checks, p95 3.76 ms, пик RSS 640 MiB; 20 VU / 20s (`read-20261114-010909-88426dd4`) — 7224 запроса, 0% ошибок, 100% checks, p95 6.64 ms, пик RSS 723 MiB. Prometheus снимки лежат в `load-results/diagnostics-20261114/`. Отдельный 1 VU / 10s подтвердил сохранение `k6-console.txt` (`read-20261114-011156-ea1fd3eb`). Эти короткие тесты не сопоставимы напрямую с исходными 3-минутными результатами. Read / 50 и 100 VU после исправления не запускались, поэтому окончательное устранение сбоя ещё не подтверждено.

Команды проверки из корня репозитория:

```powershell
$env:GOCACHE = "$PWD/apps/backend/.cache/go-build"
$env:GOTELEMETRY = 'off'
Push-Location apps/backend; go test ./...; go vet ./...; Pop-Location
python ops/load/inspect-failure.py --output load-results/diagnostics-20261114/new-window.json --start 2026-11-13T21:32:00+00:00 --end 2026-11-13T21:45:00+00:00
powershell -NoProfile -ExecutionPolicy Bypass -File ops/load/run-series.ps1 -Resume -AllowChangedConfig -MaxRuns 1
```

Следующий шаг требует отдельного согласования рискованного read / 50 VU: сначала короткий диагностический запуск с новым ID и наблюдением за RSS/cgroup, Docker VM, PostgreSQL и ошибками; затем один 3-минутный прогон с `-Resume -AllowChangedConfig -MaxRuns 1 -Execute`. Полная серия автоматически не запускается. Из-за изменения backend корректное сравнение всех девяти результатов потребует повторить четыре прежних прогона на новой версии; частичное продолжение пригодно для функционального завершения матрицы, но образует две несопоставимые когорты.

## Этап 5 — протокол испытаний 10/50/100 VU

Команда `ops/load/run-series.ps1` по умолчанию выполняет **только read-only preflight** и печатает матрицу: `public`, `read`, `mixed` × 10, 50, 100 VU; всего 9 последовательных прогонов по 3 минуты, пауза 30 секунд после каждого, кроме последнего. Режим `-Execute` применялся 13.11.2026 и был остановлен после сбоя read / 50 VU, как описано выше:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ops/load/run-series.ps1
# Только после отдельного согласования девяти прогонов:
powershell -NoProfile -ExecutionPolicy Bypass -File ops/load/run-series.ps1 -Execute
```

Перед каждым прогоном preflight проверяет `docker compose config`, `/health` backend, Prometheus target `http://backend:8080/metrics` со статусом `UP`, `current_database() = ai_buddy_load`, наличие всех `load.intern.001`…`100` и ровно 100 load-стажёров. Фиксируется базовое число заметок/событий; после каждого mixed-прогона оно должно восстановиться. При ошибке подготовки, k6, сбора метрик или очистки серия останавливается. Папка каждого прогона получает уникальный `run-id` вида `mixed-YYYYMMDD-HHMMSS-8hex`; существующая папка не перезаписывается. В `manifest.json` записываются сценарий, VU, длительность, пауза, UTC начало/конец, снимки БД, Git HEAD, признак незакоммиченных изменений и SHA-256 критичных конфигурационных файлов.

Точечная очистка реализована `cmd/cleanup-load` и Compose profile-сервисом `cleanup-load`. По умолчанию это dry-run:

```powershell
docker compose --project-name ai-buddy-load --file compose.load.yaml --env-file .env.load --profile load-tools build cleanup-load
docker compose --project-name ai-buddy-load --file compose.load.yaml --env-file .env.load --profile load-tools run --rm cleanup-load --run-id mixed-YYYYMMDD-HHMMSS-8hex
# Подставьте числа из предыдущего dry-run для того же ID:
docker compose --project-name ai-buddy-load --file compose.load.yaml --env-file .env.load --profile load-tools run --rm cleanup-load --run-id mixed-YYYYMMDD-HHMMSS-8hex --apply --expect-notes N --expect-events M
```

До любого `DELETE` команда сверяет `current_database()` с `ai_buddy_load`. Совпадение требует одновременно точного run ID и формата заголовка `load-vu-<номер>-<run-id>-<итерация>`, владельца `load.intern.<номер>@example.invalid` и фиксированного содержимого `Synthetic k6 note` или `Synthetic k6 event`. Ожидаемые количества из dry-run сверяются с фактическими в одной транзакции с короткой блокировкой записей; при расхождении транзакция откатывается. Удаляются только строки `notes` и `calendar_events`, без пользователей, чек-листов, миграций и других таблиц. Миграции не содержат внешних ключей на эти две таблицы. Повторный dry-run после очистки показывает 0/0. Старые smoke-записи с иным форматом ID эта команда намеренно не удаляет; их число входит в фиксируемый baseline.

Для каждого прогона в `load-results/<run-id>/` сохраняются `summary.json` и `metrics.ndjson` k6, `result.json` с клиентскими RPS, p50/p95/p99 (ms), долей HTTP ошибок и долей успешных функциональных проверок, `server-series.json` с Prometheus range-временными рядами: backend RPS, histogram p50/p95/p99, HTTP error rate, login RPS отдельно, CPU в cores и resident RAM в MiB. Клиентские показатели берутся только из k6 с тегом `phase=workload`; login имеет отдельный тег `phase=auth` и не входит в клиентские RPS/latency. Backend `/metrics` исключён инструментированием, Grafana исключает `/health` из пользовательского RPS. Сборщик серверных рядов дополнительно исключает `/health` и `/api/auth/login` из workload, сохраняя login отдельно. Серверные 15-секундные `rate()`-ряды анализируются начиная с 15-й секунды прогона, чтобы 30-секундная пауза исключила наложение предыдущего прогона. Источник каждой метрики обозначен в файле; клиентские и серверные значения не объединяются в одну latency или error rate.

Критерий технической успешности прогона: preflight пройден, k6 завершился с кодом 0 и предварительными порогами (`http_req_failed{phase:workload}<1%`, p95 `<2000 ms`, функциональные проверки `>99%`), оба отчёта k6 и все восемь серверных рядов получены, для mixed данные удалены только по его ID и baseline восстановлен. Эти пороги предварительные и не являются требованиями кейса. CPU/RAM относятся к процессу Go backend; histogram-квантили Prometheus приблизительны. Старые тестовые записи и фоновые healthcheck остаются в БД/метриках, но учитываются явно. Серия не гарантирует лабораторную изоляцию от постороннего трафика на стенде; перед сравнением результатов убедитесь, что им никто больше не пользуется.

Проверки подготовки 13.11.2026: PowerShell-синтаксис трёх скриптов прошёл; режим без `-Execute` проверил БД, 100 пользователей и target `UP`, напечатал 9 пунктов без нагрузки. На новом 1 VU mixed smoke dry-run нашёл 4 заметки и 3 события; `--apply` удалил ровно их, повторный dry-run дал 0/0. Подключение команды к БД `postgres` и применение с неверными ожидаемыми количествами были отклонены. Отдельный public smoke 1 VU на 20 секунд проверил структуру результатов: 99 клиентских workload-запросов, error rate 0, functional success 1, p50/p95/p99 и 8 Prometheus рядов сохранены. Позже начатая полная серия остановлена на пятом прогоне; её результаты приведены выше.

## Этап 5.4 — данные и сценарии k6 (только smoke)

В `compose.load.yaml` добавлены profile-сервисы `seed-load` и официальный `grafana/k6:1.8.2`. Они не стартуют при обычном `up`. k6 обращается только к `http://backend:8080` внутри сети `ai-buddy-load`; основной Compose не менялся. Результаты пишутся в `load-results/`, директория игнорируется Git и исключена из Docker build context. Для обоих инструментов в локальном `.env.load` нужен `LOAD_USER_PASSWORD` длиной 12–256 символов; используйте уникальный секрет и сохраняйте его между повторными запусками. Образец переменной есть в `.env.load.example`. Токены и реальные пароли не хранятся в репозитории.

Подготовка из корня проекта:

```powershell
docker compose --project-name ai-buddy-load --file compose.load.yaml --env-file .env.load config --quiet
docker compose --project-name ai-buddy-load --file compose.load.yaml --env-file .env.load --profile load-tools run --rm --build seed-load
```

`cmd/seed-load` проверяет через SQL фактическое `current_database() = ai_buddy_load` и соответствие применённой версии Goose максимальному номеру файла в `apps/backend/migrations`. Затем создаёт один общий и один backend чек-лист с этапом и заданием, синтетических Buddy/Teamlead и 100 стажёров `load.intern.001@example.invalid` … `load.intern.100@example.invalid`. Стажёры создаются через существующий `UserService.CreateInternWithAssignments`, который добавляет progress транзакционно. Повторный запуск сверяет существующих пользователей, роли, назначения и пароль, не создаёт дубликаты. `seed-demo` не используется: он требует БД `app` и Goose v7. Подготовка не обращается к `ai_buddy_test`.

Сценарии `ops/load/k6/`:

- `read`: после одного login на VU читает `/api/auth/me`, `/api/checklists`, `/api/progress`, `/api/hints`; проверяет ID пользователя, роль, наличие обоих чек-листов, прогресс и формат массива подсказок.
- `mixed`: после login на VU выполняет четыре GET (`/api/notes` и `/api/calendar/events` по два раза) и один POST (попеременно заметка или событие) в каждой итерации — **80% чтения и 20% записи** среди измеряемых запросов. Проверяет `201`, ID и поля созданного объекта, видимость предыдущей записи в личном списке и отсутствие записей другого VU с тестовым префиксом.
- `public`: читает `/api/onboarding?role=backend` и проверяет `200` и структуру сценариев.

Каждый VU использует свой аккаунт по номеру VU. Login проходит при первой итерации и помечен k6-тегом `phase:auth`; основные запросы имеют `phase:workload`. Backend Prometheus всё равно считает login как отдельный маршрут `POST /api/auth/login`, поэтому его можно исключить в PromQL фильтром `route`. Access JWT действует 15 минут; `run-k6.ps1` ограничивает длительность 14 минут. До 100 VU подготовлены учётные записи; запрос на более 100 VU скрипт отклоняет.

Воспроизводимая команда создаёт отдельную папку с уникальным ID и сохраняет `summary.json` и `metrics.ndjson`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ops/load/run-k6.ps1 -Scenario read -VUs 1 -Duration 10s
powershell -NoProfile -ExecutionPolicy Bypass -File ops/load/run-k6.ps1 -Scenario mixed -VUs 2 -Duration 10s
powershell -NoProfile -ExecutionPolicy Bypass -File ops/load/run-k6.ps1 -Scenario public -VUs 1 -Duration 10s
```

- `checklist_item_submissions`: UUID `id`, FK `progress_id`, `attempt_number > 0`, nullable `result_text`, `result_url`, `status=pending|approved|rejected`, `submitted_at`, nullable `reviewed_at`, `reviewed_by`, `review_comment`.



### 3.2. Ключевые ограничения `00003`
- Для progress: `completed_at IS NOT NULL` ровно при `completed` или `verified`; при `unavailable`/`active` — `NULL`.

- Удалён `uq_progress_one_active_per_checklist`: после reject могут одновременно существовать несколько `active` в ****одном**** чек-листе; уже открытые следующие задания не блокируются снова.

- У submission хотя бы одно из `result_text`/`result_url` должно содержать непустое после `BTRIM` значение.

- `UNIQUE(progress_id, attempt_number)`; частичный уникальный индекс допускает не более одной `pending` submission на progress.

- `pending`: нет `reviewed_at`, `reviewed_by`, `review_comment`; `approved`: есть reviewer и время; `rejected`: также обязателен непустой `review_comment`.

- Результат отправки (`result_text`, `result_url`) после создания ****неизменяем по контракту Repository/Service****; отдельного DB-триггера неизменяемости нет.

- Комментарий хранится ****в самой submission****, отдельной таблицы комментариев нет.



## 4. Бизнес-правила чек-листов
У intern два параллельных независимых чек-листа: `common` и `professional` по профессии. При создании пользователя первое задание каждого списка — `active`, остальные — `unavailable`. Открытие задания одного чек-листа не изменяет другой.



Статусы ****прогресса****: `unavailable`, `active`, `completed`, `verified`. Статусы ****отправки****: `pending`, `approved`, `rejected`; не путать их. Статуса `in_review` нет.



### 4.1. Самостоятельное задание
`ProgressService.CompleteItem(ctx, userID, itemID)` разрешён только для задания ****без**** `requires_review`. При `active → completed` устанавливает `completed_at` и сразу открывает следующее `unavailable` задание в том же чек-листе. Повторное завершение уже завершённого самостоятельного задания идемпотентно и не перезаписывает timestamp.



### 4.2. Задание с проверкой
`ProgressService.SubmitItem(ctx, userID, itemID, resultText, resultURL)`:



1. Проверяет роль intern, принадлежность задания, `requires_review`, статус `active`, непустой текст и/или URL, отсутствие конфликтующей pending-отправки.

2. В транзакции блокирует progress, определяет следующий номер попытки, создаёт immutable `pending` submission.

3. Переводит progress в `completed` с timestamp и ****сразу**** открывает следующее ещё `unavailable` задание.

4. Фиксирует всё одной транзакцией; при ошибке — rollback.



`ProgressService.ReviewSubmission(ctx, buddyID, submissionID, approved, comment)`:



1. Проверяет роль buddy, назначение стажёра через `buddy_id`, принадлежность submission, статус `pending` и корректное состояние progress.

2. Для исключения deadlock соблюдает порядок блокировок ****progress → submission**** (предварительное чтение `progress_id` из submission без блокировки допустимо).

3. Approve: `pending → approved`, progress `completed → verified`, исходный `completed_at` сохраняется; комментарий необязателен.

4. Reject: `pending → rejected`, ****обязателен непустой комментарий****, progress `completed → active`, `completed_at → NULL`.

5. Ранее открытые следующие задания ****не блокируются и не откатываются****. После reject стажёр может повторно отправить результат; история попыток сохраняется, `attempt_number` увеличивается.

6. Повторный/конкурентный review — конфликт, не повторное изменение результата.



`ReviewItem` сохранён в Service Layer как legacy-совместимый метод, но ****не опубликован в HTTP****. При финальной очистке проверить его оставшиеся вызовы и решить, нужен ли он.



### 4.3. Агрегаты
`ChecklistService.GetByUserID` читает данные в read-only `REPEATABLE READ` транзакции, проверяет соответствие всех progress-записей ожидаемым заданиям. Для каждого checklist возвращает `TotalItems`, `CompletedItems`, `CompletionPercent`. В выполненные учитываются ****`completed` и `verified`****; при reject процент может уменьшиться. `TotalItems=0` → `CompletionPercent=0`. Расчёт по каждому чек-листу отдельно.

## 6. Auth, безопасность и первый вход
- Password hashing: Argon2id (64 MiB, 3 итерации, parallelism 2, salt 16 bytes, key 32 bytes).

- JWT: HS256, TTL 15 минут, issuer `ai-buddy`, `sub` — UUID, `iat`/`exp`. `JWT_SECRET` — не менее 32 bytes; refresh token отсутствует.

- Middleware проверяет Bearer JWT и загружает ****актуальную роль из БД****, не доверяет роли в JWT.

- `AuthService.Login`: нормализует email, проверяет пароль, затем регистрирует успешный вход. Неверный email/пароль дают одинаковую ошибку `ErrInvalidCredentials`/HTTP 401.



### 6.1. Stage 4 — первый вход (реализовано по отчёту)
Поле `users.last_login_at` добавлено в `00003` и изначально `NULL`. После успешной проверки Argon2id `UserRepository.RecordLogin` выполняет ****один PostgreSQL statement****:



```sql

WITH previous AS (

    SELECT id, last_login_at IS NULL AS is_first_login

    FROM users

    WHERE id = $1

    FOR UPDATE

)

UPDATE users

SET last_login_at = CURRENT_TIMESTAMP

FROM previous

WHERE users.id = previous.id

RETURNING previous.is_first_login;

```



- Первый успешный login возвращает `is_first_login: true`, последующие — `false`.

- `last_login_at` обновляется при ****каждом**** успешном login; ошибка записи исключает успешный ответ и выдачу JWT.

- Пароль проверяется ****до**** SQL-блокировки; при двух одновременных входах одного пользователя только один должен получить `true`.

- Отчёт Codex: конкурентный интеграционный тест успешно прошёл 10 повторных запусков. SQL выглядит обоснованным для PostgreSQL `READ COMMITTED`, но независимая проверка реализации и более широких режимов изоляции не проводилась.

- `POST /api/auth/login` сохраняет существующий ответ и добавляет `is_first_login`; JWT claims и `GET /api/auth/me` не менялись.

### 13.3. Chrome Extension: аутентификация и состояние сессии

Исходники:
- `apps/extension/popup.js` — DOM, события, состояния popup, вызовы API.
- `apps/extension/popup-session.js` — чистые асинхронные функции `readToken`, `saveToken`, `clearToken`, `restoreSession` и предикат `isUnauthorized`.
- `apps/extension/popup.html`, `popup.css` — формы login/chat, секция проверки сессии и кнопка повтора.
- `apps/extension/manifest.json` — Manifest V3, разрешение `storage`, `minimum_chrome_version: 102`, host permission для локального backend.
- `apps/extension/build.mjs` — копирование файлов расширения и общего клиента в `apps/extension/dist`.

**Хранилище:** `chrome.storage.session`, ключ `accessToken`. Это сессионное хранилище расширения; оно позволяет повторно открыть popup в рамках браузерной сессии. Пароль в хранилище не записывается.

**При открытии popup:**
1. Показывается промежуточное состояние «Проверяем сессию…»; авторизованный UI скрыт.
2. `restoreSession(storage, token => getMe(backend, token))` читает JWT.
3. Нет JWT → login.
4. `GET /api/auth/me` успешен → authenticated, показываются email и чат.
5. HTTP 401 → токен удаляется, показывается login.
6. Сеть/backend временно недоступны → JWT сохраняется, показывается «Проверить снова», чат скрыт до повторной валидации.

**При входе:** `login` возвращает `access_token` и пользователя; JWT сохраняется в `storage.session`; поле пароля очищается даже при ошибке. **При выходе:** `clearToken`, очистка локального состояния, возврат к login. Общий клиент может отправить событие `ai-buddy:unauthorized`; popup завершает сессию.

**При отправке сообщения:** `chat(backend, message, accessToken)`, отображение `answer` и источников. В popup выводятся только ссылки с протоколом HTTPS (`new URL`, проверка `url.protocol === 'https:'`); ссылка открывается отдельно с `rel=noreferrer`.

**Локальный origin:** по умолчанию `http://127.0.0.1:8080`. `build.mjs` принимает `BACKEND_ORIGIN` только как origin с `http://127.0.0.1:<port>`; не считать расширение готовым к произвольному production-домену без пересмотра manifest/CSP/сборки.

## 14. Практический регламент: как добавить новую фичу или endpoint

Это рекомендуемый порядок для разработчика, впервые открывшего репозиторий. Перед изменением **сверить актуальные имена типов и сигнатуры с кодом**, а не копировать их из handoff без проверки.

### 14.1. Сначала определить место изменения

| Тип изменения | Где начинать |
|---|---|
| Новое поле или сущность | `apps/backend/migrations/` → `internal/model/` |
| SQL-запрос | `apps/backend/internal/repository/` |
| Новое бизнес-правило или транзакция | `apps/backend/internal/service/` |
| HTTP endpoint | `apps/backend/internal/handler/` или существующие handler-файлы; регистрация маршрутов в `main.go` |
| Авторизация / доступ по ролям | Существующие auth middleware и Service Layer |
| Новый вызов из UI | `packages/client/` |
| Новый экран или действие Web | `apps/web/src/components/` |
| Изменение расширения | `apps/extension/` + `build.mjs` + `manifest.json` при необходимости |
| AI-сценарий | `apps/ai/` и контракт `/api/chat` |
| Изменение API-контракта | `contracts/backend.openapi.json` и тесты |
| Сквозной пользовательский сценарий | `tests/e2e/` |

Путь к HTTP handler зависит от фактической структуры текущего репозитория: **не создавать новую директорию только ради следования таблице**, если существующие handlers находятся иначе.

### 14.2. Пошаговый процесс

1. **Сформулировать контракт:** кто вызывает, с какой ролью, входные поля, успешный ответ, HTTP-коды ошибок, изменения состояния.
2. **Проверить существующие реализации:** поискать похожие route, DTO, методы Service/Repository, тесты и общие клиентские функции; не дублировать их.
3. **При необходимости спроектировать миграцию:** добавить новую `0000N_*.sql` с `Up/Down`, ограничениями, индексами и учётом существующих данных. Не переписывать уже применённые миграции.
4. **Обновить модель:** типы Go и nullable-поля должны соответствовать SQL (`*time.Time`, `*int` и т. п.).
5. **Реализовать Repository:** только SQL и преобразование строк, `context.Context`, `DBTX`, параметры `$1`, `$2`, корректные ошибки. Транзакцию здесь не открывать.
6. **Реализовать Service:** права доступа, доменные проверки, переходы статусов, атомарность и блокировки. Для нескольких записей — `withTransaction`.
7. **Реализовать HTTP handler:** строгий JSON, проверка UUID, получение пользователя из auth context, вызов Service, безопасное отображение доменных ошибок в HTTP. Не доверять `user_id`/`buddy_id` из тела запроса вместо JWT.
8. **Зарегистрировать маршрут** в существующей маршрутизации `main.go` и применить нужную auth/role-защиту.
9. **Обновить OpenAPI и общий клиент:** метод, DTO, заголовок Bearer, типы и ошибки.
10. **Подключить Web/Extension:** состояние загрузки, успешный результат, ошибки и обновление UI; использовать доступные роли и labels.
11. **Добавить тесты:** Repository (SQL/constraints), Service (правила/rollback/конкурентность), Handler (`httptest`, права и коды), клиент и E2E при необходимости.
12. **Проверить и задокументировать:** тесты, сборка, diff; актуализировать `ИНФА.md` и этот файл.

### 14.3. Минимальная матрица тестов нового endpoint

| Случай | Ожидаемая проверка |
|---|---|
| Успех | Точный статус, тело ответа, сохранение в БД |
| Без JWT | 401 |
| Неверная роль | 403 |
| Чужой приватный ресурс | 404 без утечки существования |
| Неверный JSON/UUID | 400 |
| Неизвестное поле JSON | Отклонение при строгом декодировании |
| Повторное действие / конфликт | 409 либо документированная идемпотентность |
| Ошибка SQL внутри транзакции | Rollback всех изменений |
| Конкурентные запросы | Нет двойных попыток, review или повреждённых статусов |
| Регрессия | Существующие тесты и сценарии не ломаются |

Конкретные коды ошибок сверять с текущим контрактом соответствующего endpoint: таблица — ориентир, не универсальная спецификация.

### 14.4. Команды для проверки backend

```bash
cd apps/backend

# Тестовая БД должна быть отдельной, с актуальными миграциями:
go test -count=1 -p 1 ./...
go test -race ./...
go vet ./...
go build ./...
test -z "$(gofmt -l .)"
```

Из корня:

```bash
npm test
npm run build
git diff --check
```

При необходимости дополнительно проверить `contracts`, живые HTTP-сценарии и Playwright. Наличие PASS при пропущенных интеграционных тестах не означает, что SQL-часть проверена.

### 14.5. Пример архитектурного маршрута новой фичи

Допустим, нужно добавить для intern действие «отметить знакомство с документом». Сначала определить, является ли это новым типом существующего checklist item: если да, **предпочесть расширить существующие Complete/ProgressService**, а не добавлять новую таблицу и параллельную систему статусов.

Если всё же нужен отдельный endpoint, цепочка такая:

```text
POST /api/...                 → HTTP handler
  ├─ JWT и роль intern        → middleware / auth context
  ├─ JSON + UUID              → handler validation
  └─ выполнить действие       → Service
       ├─ проверить владельца → Repository read
       ├─ проверить статус    → доменное правило
       └─ изменить данные     → Repository SQL в транзакции
                                  ↓
                               PostgreSQL
```

После этого: OpenAPI → `packages/client` → Web/Extension → тесты. Это **иллюстрация порядка работы**, не описание уже существующего маршрута.

## 15. Точка продолжения для следующего разработчика

1. Читать **весь** документ: разделы 1–12 содержат подробную модель и инварианты; разделы 13–14 — более свежие сведения и инструкцию по расширению.
2. Проверить ветку, `git status`, фактические migrations/handlers и текущие DTO перед изменением.
3. Сохранять инварианты: две независимые последовательности; `completed` и `verified` учитываются в процентах; submit открывает следующее; reject возвращает только исходное; история попыток сохраняется; buddy видит только своих intern.
4. Не запускать разрушительные SQL/Goose операции на основной БД и не удалять Docker volume.
5. При существенной фиче сначала согласовать контракт и изменения схемы, затем реализовать минимально достаточное решение и проверить тестами.

## 16. Дополнение: Backend для хакатона (Goose v7)

В актуальном коде три роли: `intern`, `buddy`, `teamlead`. Buddy создаёт стажёра и проверяет результаты; teamlead добавляет персональные задания и видит профессиональный прогресс только назначенных стажёров. Общий прогресс intern и buddy охватывает общий и профессиональный чек-листы. ML-профессия поддерживается в коде; демонстрационный SQL-чек-лист подготовлен отдельно и не запускается автоматически. Новые даты рождения и начала работы nullable для старых пользователей; `age_years` и `tenure_months` вычисляются при чтении профиля.

Корпоративный справочник загружается из `data/corporate_employees.json`; заявку на инструмент создаёт только подтверждённый пользователем вызов Backend с проверкой корпоративной личности и прав. Заявки сохраняются в `corporate_access_requests`; чтение ограничено владельцем, повторы защищены ключом идемпотентности. Текущий AI `POST /chat` остаётся информационным, `POST /hint` используется для подсказок; создание заявки через естественный язык требует отдельного согласования структурированного контракта с AI-командой. Полные маршруты, DTO, примеры, коды ошибок и граница ответственности: [Backend corporate integration](docs/backend-corporate-integration.md). Основную БД `app` до Goose v7 в этой работе не обновляли.
