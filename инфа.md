## 1. Назначение

AI-Buddy — MVP для сопровождения стажёра во время онбординга. Система помогает видеть этапы адаптации, выполнять задачи чек-листов, получать обратную связь от наставника (buddy) и задавать вопросы AI-помощнику. Проект разрабатывается для хакатона; приоритет — воспроизводимый рабочий сценарий без избыточной архитектуры.

### Основные сценарии

- Авторизация пользователя и получение его профиля.
- HR Sync создаёт учётную запись стажёра по снимку Mock HR.
- Стажёр видит общий и профессиональный чек-листы, задачи и прогресс.
- Для задач предусмотрены статусы и, где требуется, проверка наставником.
- Стажёр задаёт вопрос AI-помощнику и получает ответ со ссылками на демонстрационные внутренние ресурсы.
- AI-помощник доступен в веб-интерфейсе и Chrome-расширении.

Используются демонстрационные и синтетические данные. Интеграции с корпоративными сервисами допускают имитацию.

## 3. Модель данных и бизнес-логика

Базовые сущности backend: `users`, `checklists`, `checklist_items`, `user_checklist_progress`. В последующих миграциях добавлены стадии чек-листов и роль buddy. Пользователи имеют роли; для стажёров предусмотрено профессиональное направление (например, backend/frontend/ml).

При создании стажёра сервис инициализирует прогресс по общему и профессиональному чек-листам транзакционно. Задачи внутри чек-листа выполняются последовательно; независимые чек-листы могут продвигаться параллельно. Для задач с проверкой наставника предусмотрен отдельный сценарий подтверждения.

Схему, точные поля и актуальные HTTP-контракты следует сверять с миграциями и кодом `apps/backend/`; этот документ не заменяет спецификацию API.

## 4. Авторизация

- Используется JWT-авторизация.
- `POST /api/auth/login` — вход пользователя.
- `GET /api/auth/me` — проверка токена и получение текущего пользователя.
- Защищённые запросы используют `Authorization: Bearer <token>`.
- Учётные записи и назначения Buddy/Teamlead создаёт `cmd/sync-hr` из Mock HR после инициализации каталога чек-листов. Первичные пароли новых пользователей сохраняются в закрытом файле вне репозитория.

## 5. Chrome-расширение

Расширение поддерживает вход, выход и авторизованные запросы к AI-помощнику. JWT хранится в `chrome.storage.session`, а не в постоянном `chrome.storage.local`.

Логика открытия popup:

1. При наличии сохранённого JWT выполняется запрос `/api/auth/me`.
2. До подтверждения токена защищённый интерфейс не показывается.
3. При `401` токен удаляется, пользователь возвращается к форме входа.
4. При временной сетевой ошибке токен сохраняется; доступна повторная проверка соединения.
5. При выходе сессия очищается.

Сессионная логика выделена в `apps/extension/popup-session.js`, а сборка подключает этот модуль в MV3-артефакт. Для `chrome.storage.session` установлен минимальный поддерживаемый Chrome 102.

### Сквозные сценарии

1. HR Sync создаёт стажёра и назначает Buddy/Teamlead; стажёр входит в web, открывает общий и профессиональный чек-листы, проверяет задачи и прогресс, задаёт вопрос AI-помощнику.
2. Chrome MV3 popup входит под наставником, отправляет авторизованный вопрос, закрывается и открывается повторно с сохранённой сессией, затем выполняет logout с удалением JWT.

E2E использует ARIA-роли и доступные имена вместо привязки к внутренним CSS-классам. Тестовый стажёр создаётся с уникальным email. Публичного безопасного API удаления стажёра нет; дополнительный endpoint или прямое SQL-удаление для теста не вводились. Сценарий рассчитан на изолированную тестовую БД.

## 9. Актуальный Backend для демо

В текущем Backend три роли: `intern`, `buddy`, `teamlead`; buddy проверяет результаты, teamlead добавляет персональные задания. Общий, Backend, Frontend и ML-чек-листы загружает `cmd/init-catalog`. Корпоративный mock использует синтетические записи из `data/corporate_employees.json` и серверную проверку разрешённых инструментов. Заявки Service Desk создаются через подтверждённый запрос Backend с ключом идемпотентности и сохраняются в PostgreSQL. Действия из AI-чата пока не поддерживаются: AI-команде нужен структурированный контракт предложения действия. Подробности и примеры: [Backend corporate integration](docs/backend-corporate-integration.md). Сведения о прежней Goose v7 и старой основной БД приведены выше как история проекта.
## Краткая карта фактической архитектуры — 2026-11-13

- `apps/web`: React SPA. Управляет UI, history routes и browser session; все решения о правах оставляет Backend.
- `packages/client`: типизированная граница HTTP для Web/Extension; содержит login/refresh/logout и методы предметных API.
- `apps/backend/internal/handler`: декодирование HTTP, JWT/session middleware, role guards, DTO и безопасное отображение ошибок.
- `apps/backend/internal/service`: бизнес-правила и транзакции создания стажёра, progress/review, персональных задач, корпоративных заявок и refresh-сессий.
- `apps/backend/internal/repository`: параметризованный SQL, user-scoped чтение/изменение данных.
- `apps/backend/migrations`: единственный источник схемы PostgreSQL, актуальная версия 7.
- `data/corporate_employees.json`: синтетический корпоративный справочник, загружаемый Backend при старте.
- `apps/ai`: неизменённый mock AI. Backend отправляет ему только текст сообщения.
- `apps/extension`: неизменённый MV3 клиент.

Ключевые границы доверия: access JWT содержит идентификатор сессии; middleware сверяет активную refresh-сессию и заново загружает пользователя. Backend берёт actor только из контекста JWT. Доступ buddy/teamlead к стажёру одновременно ограничивается локальными `buddy_id`/`teamlead_id`; корпоративный справочник не заменяет локальную авторизацию. Личные заметки, события и заявки фильтруются по actor `user_id` в SQL.

Риски: корпоративный источник не сетевой и не демонстрирует latency/retry/подпись ответов; AI mock не возвращает действия и не работает как LLM; отсутствует административный lifecycle demo-пользователей; MV3 Playwright зависит от браузера, поддерживающего headless extension service workers. Обновление production-БД не начинается автоматически и требует отдельного runbook/окна/backup.

## Актуализация после консолидации (14.11.2026)

Актуальная схема для **чистой БД** создаётся единой Goose-миграцией `00001_init.sql`, структурно соответствующей прежней v9. История v8/v9 существующих БД не меняется. `cmd/init-catalog` отдельно и идемпотентно создаёт общий и три профессиональных чек-листа. `cmd/sync-hr` создаёт пользователей, назначения Buddy/Teamlead и недостающий прогресс из Mock HR; ручное назначение Teamlead через API удалено. Первичные пароли новых пользователей находятся только в закрытом JSON-файле вне репозитория, указанном через `-credentials`; в PostgreSQL — хеши. Актуальные команды запуска приведены в README. Предыдущие разделы этого файла описывают исторические этапы проекта.
